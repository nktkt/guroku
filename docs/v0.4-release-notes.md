# guroku 0.4 — "It's usable"

The 0.3 release made guroku fast. The 0.4 release makes it usable. Up through
0.3, guroku could resolve a graph and lay down a strict `node_modules`, but the
moment your project leaned on a `postinstall` hook, a `package.json` script, or
a binary in `.bin/`, you were back to running another package manager
alongside it. With 0.4 those gaps are filled in: lifecycle scripts run, `guroku
run` and `guroku exec` work the way you'd expect them to, `node_modules/.bin/`
is populated, workspaces are discovered, and `.npmrc` is read. None of the
0.3 internals — the content-addressable store, the strict layout, the
hardlink linker — changed shape. What changed is that you can now drive a real
project end to end with `guroku` and nothing else.

This document is the prose narrative for 0.4.0. The terse, change-by-change
list lives in [`CHANGELOG.md`](../CHANGELOG.md).

## What's new

### Lifecycle scripts

guroku now runs the standard npm lifecycle scripts during install:

- For the project itself: `preinstall`, `install`, `postinstall`, and
  `prepare`.
- For each dependency: `preinstall`, `install`, and `postinstall`.

Scripts run after the dependency's files have been linked into place, so a
`postinstall` that reaches into its own package directory sees a fully
populated tree. Project-level `prepare` runs at the end of the install, after
every dependency hook has resolved.

If a script exits non-zero, the install fails fast and surfaces the package
name, the script name, and the captured stderr. There is no silent skip.

If you don't want any of this — for a hardened CI build, or for a project
whose dep tree contains a `postinstall` you don't trust — pass
`--ignore-scripts` to `guroku install` and every hook is skipped.

### `guroku run [<script>] [-- <args>]`

`guroku run` runs a script defined in your project's `package.json`. With no
argument, it lists the available scripts. With a script name, it runs it.
Anything after `--` is forwarded verbatim to the underlying command, so:

```
guroku run test -- --reporter=verbose --bail
```

passes `--reporter=verbose --bail` to whatever your `test` script invokes.
`PATH` inside the script is prepended with `node_modules/.bin/`, the same way
`npm run` does it, so unqualified binary names resolve to the project's own
copy.

### `guroku exec <cmd>`

`guroku exec` runs a single command with the project's binary directory on
`PATH`. Lookup order is `node_modules/.bin/` first, then the inherited `PATH`.
This is the escape hatch when you don't want to wrap the call in a
`package.json` script:

```
guroku exec eslint src/
guroku exec tsc --noEmit
```

### `guroku workspaces`

guroku now discovers monorepo sub-packages. If your root `package.json`
declares a `workspaces` field — either as an array of globs or as the object
form — `guroku workspaces` walks the tree, resolves each glob, parses each
member's `package.json`, and prints the discovered set.

Discovery is the first half of workspace support. Linking inter-workspace
dependencies (so that `packages/app` depending on `packages/lib` resolves to
the local copy instead of the registry) is slated for v0.5; see "Known
limitations" below.

### `node_modules/.bin/` shims

For every direct dependency that declares a `bin` entry in its
`package.json`, guroku now creates a launcher under `node_modules/.bin/`.
This means `./node_modules/.bin/vitest`, `./node_modules/.bin/tsc`,
`./node_modules/.bin/eslint`, and so on all exist after `guroku install`,
without you having to do anything extra. `guroku run` and `guroku exec`
both rely on this directory.

Only direct dependencies get top-level shims. Transitive packages' bins are
reachable through the strict layout but are deliberately not hoisted into
the top-level `.bin/`.

### `.npmrc` reading

guroku reads `.npmrc` from two locations, in order:

1. The project root (`./.npmrc`).
2. The user's home (`~/.npmrc`).

The project file overrides the user file on a per-key basis. The keys that
0.4 actually consumes are:

- `registry` — overrides the default registry URL.
- `//registry.example.com/:_authToken` — parsed and stored in config, but
  not yet sent on requests; see "Known limitations."

Other keys are parsed and ignored.

### `--ignore-scripts` flag for `guroku install`

`guroku install --ignore-scripts` skips every lifecycle hook, project-level
and per-dependency. The dependency graph, store contents, and `node_modules`
shape are otherwise identical to a normal install. This is the recommended
flag for CI environments that want lockfile-pinned, hook-free, reproducible
builds.

## What this means in practice

A few concrete shifts from how you used guroku in 0.3:

- **Running tests.** You can stop typing `node node_modules/.bin/vitest` (or
  shelling out to npm just to run a script). `guroku run test` works the
  way `npm run test` does, including `-- --flag` argument forwarding.
- **The new hardened CI invocation.**
  `guroku install --frozen-lockfile --ignore-scripts` is what you want in CI:
  the lockfile is enforced, no hook from any dependency runs, and the
  install is fully reproducible from inputs you can audit.
- **Examples that need hooks actually work.**
  `cd examples/with-scripts && guroku install` will run `preinstall`,
  `install`, `postinstall`, and `prepare` for the example project, plus
  every dependency hook in its tree. In 0.3 these were skipped with a
  one-liner; in 0.4 they run.

## Breaking changes

- **Lifecycle scripts run by default.** If you were relying on guroku 0.3's
  silent skipping of `postinstall` hooks — for example, if some package in
  your tree has a postinstall that doesn't work in your environment and
  things were quietly fine — you'll need to pass `--ignore-scripts` to keep
  the old behavior. The default flipped, on purpose.
- **`Manifest::scripts`, `Manifest::bin`, and `Manifest::workspaces` are
  typed fields.** In 0.3 these were captured by the catch-all `other` map,
  so consumers that read `manifest.other.get("scripts")` got back the JSON
  blob. In 0.4 those keys are extracted into typed fields on `Manifest`
  before `other` is populated, so `manifest.other.get("scripts")` now
  returns `None`. Read `manifest.scripts`, `manifest.bin`, and
  `manifest.workspaces` instead.

Both items are covered in more detail in
[`docs/migration/v0.3-to-v0.4.md`](migration/v0.3-to-v0.4.md).

## What didn't change

- **Store layout.** Still `~/.guroku/cas/<sha[0:2]>/<sha[2:]>/`. A CAS
  populated by 0.3 is reused as-is by 0.4.
- **Strict `node_modules` layout.** Still
  `node_modules/.guroku/<name>@<version>/node_modules/<name>/` with
  symlinks at `node_modules/<name>`. The new `.bin/` directory sits
  alongside, not on top of, the existing layout.
- **Lockfile schema.** Still `lockfileVersion: 1`. A `guroku.lock`
  written by 0.3 is read by 0.4 without modification.
- **Install pipeline.** The fetch / verify / link / record stages are
  unchanged. Lifecycle scripts run as a new stage after linking, not by
  reordering existing ones.
- **Resolver.** Still BFS, sticky-first: the first version that satisfies
  a constraint is preferred for the rest of the resolve, and downgrades
  only happen when forced.

## Known limitations

- **No `npm_*` environment variables during scripts.** Some legacy
  `postinstall` scripts read `npm_package_version`, `npm_config_*`, and
  similar variables. guroku 0.4 does not set them. Scripts that need them
  will fail or misbehave; reach for `--ignore-scripts` and run the offending
  step out of band, or wait for a follow-up that wires the env up.
- **Workspaces are discovered but inter-deps are not auto-linked.**
  `guroku workspaces` will list every member, but if `packages/app`
  depends on `packages/lib` it will still try to resolve `lib` from the
  registry. Inter-workspace linking is the headline feature of v0.5.
- **`.npmrc` `_authToken` is parsed but unused.** The token is read from
  both the project and user `.npmrc` and stored in config, but not yet
  attached to outbound registry requests. Private registries that require
  auth still won't work in 0.4. Wiring this through is v0.5.
- **No `guroku dlx` yet.** The "fetch a package into a temporary
  environment and run its bin" subcommand is planned for a v0.4.x point
  release.
- **No `guroku run -ws <script>` yet.** Running a script across every
  workspace member with a single command is planned for v0.4.x; for now
  you'll need to loop in your shell.

## Coming in v0.5

- **Workspace inter-dependency linking.** `packages/app` depending on
  `packages/lib` will resolve to the local member, not the registry, and
  the link will be a symlink into the workspace member's source directory.
- **Registry auth tokens.** The `_authToken` parsed out of `.npmrc` in 0.4
  will actually be sent on metadata and tarball requests, unlocking
  private registries.
- **Git, file, and local dependencies.** Spec strings of the form
  `git+https://...`, `file:./vendor/foo`, and `link:../sibling` will be
  resolvable, alongside the existing registry-backed deps.
