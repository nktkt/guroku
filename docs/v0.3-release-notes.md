# guroku 0.3 — "It's fast"

The 0.3 release is the first one where guroku starts to feel like a tool you'd
actually reach for. Resolution, fetching, and linking have all been reworked
around a content-addressable store and a strict pnpm-style `node_modules`
layout, so a warm install is dominated by hardlink syscalls rather than tarball
extraction or network round-trips. The CLI surface and lockfile schema are
unchanged from 0.2; what's different is what happens underneath when you type
`guroku install`.

This document is the prose narrative for 0.3.0. The terse, change-by-change
list lives in [`CHANGELOG.md`](../CHANGELOG.md).

## What's new

### Content-addressable store at `~/.guroku/cas/`

Package contents are now keyed by their SHA, not by `name@version`. The
on-disk shape is:

```
~/.guroku/cas/<sha[0:2]>/<sha[2:]>/
```

Two projects that depend on the same `lodash@4.17.21` no longer pay for the
bytes twice — the second project's resolver verifies the integrity hash, finds
the directory already populated, and skips the fetch and the extract entirely.

Integrity is verified on insert, not on every read, which keeps the warm path
cheap.

### Hardlink-based linker

`node_modules` is now populated by hardlinking individual files out of the CAS
rather than copying or extracting them. For a warm cache, this means populating
a project's `node_modules` is essentially a walk of the resolved graph plus one
`link(2)` per file — no decompression, no I/O of package contents, no network.

On filesystems that don't support hardlinks across the relevant boundary (rare
on a single volume, but possible with some container setups), guroku falls back
to copying and logs a warning once per install.

### Strict pnpm-style layout

The on-disk shape under `node_modules` is now:

```
node_modules/.guroku/<name>@<version>/node_modules/<name>/
node_modules/<name> -> .guroku/<name>@<version>/node_modules/<name>
```

Each package only sees its declared dependencies, because each package's own
`node_modules` directory only contains symlinks to the packages it actually
depends on. This eliminates the "phantom dependency" class of bug, where code
imports a package it never declared and happens to work because some other
dependency hoisted it.

The top-level `node_modules/<name>` entries are symlinks into `.guroku/`, so
tools that resolve via `fs::canonicalize` or `realpath` see the real path
inside the store-shaped tree.

### Parallel root-metadata prefetch

The resolver now fetches root-level metadata for every direct dependency in
parallel before it starts walking the graph. On projects with a wide
dependency tree, this overlaps almost all of the registry I/O with the
resolver's own work, instead of serializing them.

### ETag-aware HTTP cache for registry metadata

Registry metadata responses are cached on disk with their `ETag` headers. On
subsequent installs, guroku sends `If-None-Match` and the registry replies
with a `304 Not Modified` instead of re-sending the full document. For a
project of any real size, this turns "megabytes of metadata over the wire"
into "a handful of small 304 responses."

## What this means in practice

Rough before/after sketch, with everything qualitative for now:

- **First install ever (cold cache, cold project).** Comparable to v0.2.
  You're bottlenecked on the registry and on tarball extraction, and 0.3
  doesn't change either of those fundamentally.
- **Second install of the same project (warm cache).** Dramatically faster.
  Metadata requests turn into 304s, and every package is already in the CAS,
  so linking is a hardlink walk.
- **First install in a *different* project that shares dependencies.**
  Significantly faster than v0.2. The CAS is global, so any package that any
  prior project pulled is already extracted; only genuinely new packages are
  fetched.

## Breaking changes

- The on-disk store layout has moved from
  `~/.guroku/store/<name>/<version>/` to
  `~/.guroku/cas/<sha[0:2]>/<sha[2:]>/`. Old contents under
  `~/.guroku/store` are not migrated; they are harmless to leave in place
  and safe to remove (`rm -rf ~/.guroku/store`).
- `node_modules/<name>` is now a symlink, not a regular directory. Tools
  that resolve paths via `fs::canonicalize` or `realpath(3)` see the right
  thing. Tools that hard-code `node_modules/<name>` as a regular directory
  — for example, by `stat`-ing it and checking `S_ISDIR` without following
  symlinks — may need to be updated to follow the link.

Both items are covered in more detail in
[`docs/migration/v0.2-to-v0.3.md`](migration/v0.2-to-v0.3.md).

## What didn't change

- **CLI surface.** Still `guroku install`, `guroku add`, `guroku remove`,
  with `--frozen-lockfile` for CI. No flags were renamed or removed.
- **Lockfile schema.** Still `lockfileVersion: 1`. A `guroku.lock` written
  by 0.2 is read by 0.3 without modification, and vice versa, as long as
  no new resolver behavior is triggered.

If you're upgrading and your only contact with guroku is the CLI plus the
lockfile, the 0.2 -> 0.3 jump should be invisible apart from being faster.

## Known limitations

- **Peer auto-install** is still slated for v0.4. 0.3 still warns on
  unsatisfied peer dependencies but does not install them automatically.
- **Lifecycle scripts** (`preinstall`, `install`, `postinstall`) are still
  slated for v0.4. 0.3 will skip them with a one-line notice per package.
- **No `guroku store gc` yet.** The CAS grows monotonically. A garbage
  collection subcommand that walks every project's lockfile and prunes
  unreferenced CAS entries is on the v0.4 roadmap.
- **Windows symlink support** requires Developer Mode (or running as
  Administrator). Without it, `node_modules/<name>` symlinks can't be
  created and guroku falls back to copying, which negates most of the
  warm-install win.

## What's coming in v0.4

- Lifecycle scripts: `preinstall`, `install`, `postinstall`, with a sandboxed
  execution model and clear opt-out.
- Workspace support: a single lockfile and a single CAS-backed
  `node_modules` graph spanning multiple packages in a monorepo.
- `guroku run` and `guroku exec`: run package scripts and binaries from
  installed dependencies without going through a separate task runner.
