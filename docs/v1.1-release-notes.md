# guroku 1.1 — "It resolves better"

guroku 1.0 was the release where we stopped moving the floor. Nine
months of iteration on lockfile shape, resolver entry points, and CLI
flags settled into a single commitment: SemVer-stable lockfile, Rust
prelude, and CLI. Embedders could pin `guroku-core = "1"` and stop
holding their breath on every `cargo update`. That was, deliberately,
not a feature — it was the absence of churn.

1.1 is the first release that uses that runway. With the public surface
frozen, we can finally spend an entire cycle on additive features:
new resolution semantics, a smarter resolver, better error messages,
and a few quality-of-life improvements that have been blocked on
"we'd have to break X to ship this." Now we don't have to break X. We
just add new fields, new variants, new behavior — and old code keeps
compiling and old lockfiles keep loading.

This document is the prose companion to `CHANGELOG.md`. The changelog
is the terse, scannable list. This is the narrative: what shipped,
why, what it means in practice, and where we go next.

## What's new

### npm aliases

You can now install a package under a different name than its
registry name:

```json
{
  "dependencies": {
    "my-cool-name": "npm:lodash@^4.17"
  }
}
```

This installs lodash and exposes it as `my-cool-name` in your import
graph. The most common reason to want this is side-by-side versions of
the same package: you can have `lodash-4` and `lodash-3` in the same
project, both resolving to real lodash releases, without forking either
of them.

The syntax follows the npm/yarn convention exactly: `npm:<name>@<spec>`.
The aliased name is what appears in your `node_modules`-equivalent
layout and what `require`/`import` resolves. The underlying registry
package is what gets fetched, deduplicated, and locked. Aliased entries
appear in the lockfile with a new `aliased_from` field (added as an
optional field, per the lockfile stability commitment).

See `docs/aliases.md` for the full reference, including how aliases
interact with the resolver, the store, and `peerDependencies`.

### Path-keyed overrides

Flat overrides are a blunt instrument. If you write:

```json
{ "overrides": { "left-pad": "1.3.0" } }
```

every `left-pad` in your dependency graph gets pinned to 1.3.0,
regardless of who pulled it in or why. That is sometimes what you
want, but very often what you actually meant was "pin left-pad, but
only when it shows up under build-tool X."

1.1 adds path-keyed overrides:

```json
{
  "overrides": {
    "webpack > terser-webpack-plugin > terser": "5.16.0"
  }
}
```

The key is a `>`-separated chain of package names from a top-level
dependency down to the leaf you want to pin. The pin only applies when
the resolver reaches that exact leaf through that exact chain. Other
copies of `terser` elsewhere in the graph are untouched.

This is less aggressive than flat overrides and is usually what you
want when you are working around a specific transitive issue. Flat
overrides still exist; they win when you actually do mean "everywhere."

The full grammar and resolution rules live in `docs/overrides.md`.

### Glob resolutions

Yarn-style `resolutions` with the `**/<name>` pattern now actually
match. Previously the field was parsed and stored in the manifest, but
the matcher had a TODO comment and silently never fired. As of 1.1:

```json
{
  "resolutions": {
    "**/foo": "1.0.0"
  }
}
```

pins every `foo` in the graph, at any depth, to 1.0.0. This is closer
in spirit to flat overrides than to path-keyed overrides — the leaf
name is what matters, the path doesn't. Use it when you need a
hammer and don't care which nail.

Richer glob shapes (`pkg/**/foo`, `*-helper`, etc.) still parse without
error but do not match anything. We didn't want to silently break
manifests that had been relying on the parse-but-no-op behavior. See
"Known limitations" below.

### Single-step backtracking on diamond conflicts

The 1.0 resolver was strictly greedy. When it picked a version of
package A and then discovered that A's choice forced a version of B
that conflicted with a constraint elsewhere in the graph, it gave up
and reported a `ResolutionConflict` error. This produced false
negatives on graphs that had a perfectly valid solution if you just
picked a slightly older A.

1.1 introduces single-step backtracking. When the resolver hits a
conflict, before erroring it tries substituting a different already-
seen version of one of the packages on the conflict path. If the
substitution makes the conflict go away, the install succeeds. If it
doesn't, the error fires as before — but now with much better
diagnostics (see below).

This is a deliberately limited form of backtracking: it only revisits
one already-chosen package, and it only tries versions the resolver
has already had to consider. That handles the common diamond cases
without the implementation cost or the worst-case runtime of a full
SAT/PubGrub solver. The full algorithm is documented at
`docs/internals/single-step-backtrack.md`.

### Conflict messages with paths

When the resolver does give up, the error now includes the full chain
that led to the conflicting requirement. The 1.0 message read:

```
ResolutionConflict {
  package: "foo",
  requested: "^1.0",
  found: "2.0.0",
  requested_by: "bar",
}
```

which told you `bar` wanted a different `foo`, but not how `bar` got
into your graph. The 1.1 message reads:

```
ResolutionConflict {
  package: "foo",
  requested: "^1.0",
  found: "2.0.0",
  requested_by: "my-app > some-tool > bar",
}
```

so you can immediately see where to apply a path-keyed override or
where to file the upstream issue. The shape change is documented in
"Breaking changes" below.

## What this means in practice

A few concrete workflow improvements you can expect:

You can stop forking packages just to rename them. The classic case is
needing two major versions of the same library in the same project:
in 1.0 you either vendored one of them or published a renamed mirror
to your private registry. In 1.1 you alias.

You can stop pinning a leaf globally when you really only meant
"when webpack pulls it." The 1.0 advice for these situations was
"flat-override the leaf and accept that it applies everywhere." That
was usually fine, occasionally caused surprises in unrelated parts of
the graph, and was annoying to reason about during code review. Path-
keyed overrides let you say what you actually mean.

Some installs that errored in 1.0 with `version conflict for X` now
succeed without any manifest changes. If you have been carrying a
flat override solely to unblock the resolver on a diamond, you can
probably remove it now and let the new backtracking step handle it.
Run `guroku install --dry-run` after deleting the override and watch
the resolution log to confirm.

## Breaking changes

There are no breaking changes to the documented public surface — that
is, the items reachable through `guroku::prelude` and their published
signatures. Per the v1.0 SemVer commitment, those won't move in a 1.x.

There are, however, three changes to types that consumers occasionally
reach for outside the prelude or pattern-match against. They are
listed here for completeness:

**`DepSpec` is now `#[non_exhaustive]`.** External code that does
`match spec { DepSpec::Registry(_) => ..., DepSpec::Git(_) => ..., ... }`
without a `_` arm will now fail to compile. Add the wildcard arm. We
made this change so future spec kinds (we have `npm:<alias>` in 1.1
and probably a `bundle:` form coming) can be introduced as additive
variants without breaking exhaustive matches. This is the standard
Rust pattern for an enum that is expected to grow.

**`Resolved` gained an `aliased_from: Option<String>` field.** Library
consumers who construct `Resolved` literals (this is rare — it mostly
shows up in test fixtures and embedders) need to add
`aliased_from: None` to those literals. `Resolved` is not marked
`#[non_exhaustive]` for backwards-compat reasons; the next time we
add a field to it, we will mark it. Until then, treat it as if it
were.

**`ResolutionConflict.requested_by` shape changed from `"<parent>"` to
`"<chain>"`.** This is the one user-observable change to a stable type.
The field is still a `String`, the old code that printed it still
prints something useful, but if you have code that parses this string
to extract a single package name, that code now needs to split on
`" > "` and take the last segment. The error message itself reads
better; the parse cost is on consumers who were depending on the old
shape. We considered adding a separate `requested_by_chain: Vec<String>`
field and leaving `requested_by` alone, but the existing field was
already a freeform string, was already documented as "human-readable
diagnostic," and we didn't want two fields meaning almost the same
thing.

Per the v1.0 SemVer commitment, none of these break the documented
public surface. They are visible to code that has reached past the
prelude or pattern-matched on internal-shaped types — which is allowed,
but explicitly outside the stability guarantee.

## What didn't change

The CLI surface is identical. Every flag, every subcommand, every
exit code that worked in 1.0 works the same way in 1.1. New flags
have been added (`--alias`, `--explain-resolution`); none have been
removed or repurposed. CI pipelines pinning specific `guroku`
invocations will not need updating.

The lockfile schema is the same. `lockfileVersion: 1` still reads. The
new `aliased_from` field is an additive optional field, exactly the
kind of change the 1.0 stability promise allowed for. 1.0 readers
ignore it; 1.1 readers populate it when relevant. No migration step
is required.

The store layout is unchanged. Aliased packages share a store entry
with their underlying registry package — the alias is a name in the
project layout, not a separate copy on disk. If you have a 1.0 store
on disk, 1.1 reads and writes it without modification.

The install pipeline — fetch, verify, link, run lifecycle scripts — is
byte-for-byte the same. Lockfile-based installs produce identical
trees to 1.0.

All v1.0 features are present: workspaces, file/git deps, peer
dependencies, optional dependencies, scripts, audit, private
registries, the embedding API. Nothing was removed.

## Resolver upgrade in detail

The 1.0 resolver was a depth-first walk with a single-pass constraint
check. For each package, it picked the highest version satisfying the
constraints seen so far, recorded the choice, and moved on. If a later
constraint conflicted with an earlier choice, it errored.

1.1 adds a single backtracking step on conflict. The high-level
algorithm:

1. Walk the graph as in 1.0, recording each (package, version) choice
   and the constraint that justified it.
2. On constraint conflict for package P, look at the chain of choices
   that led here. For each ancestor A on the chain, ask: is there a
   different version of A that the resolver had to consider (i.e. one
   that appeared in A's candidate list) and that, if substituted in,
   would resolve the conflict on P?
3. If yes, substitute the first such candidate and resume resolution.
4. If no, raise `ResolutionConflict` with the full chain.

This handles the common diamond cases — A pulls B@^1, A pulls
C which pulls B@^2 — by stepping A back to a version of A that pulls
B@^2, when one exists. It does not handle deeper conflicts that
require revisiting multiple ancestor choices, and it does not enumerate
the full search space. Those cases still error.

The full algorithm, the candidate-list bookkeeping, the termination
proof, and the worst-case complexity analysis are written up at
`docs/internals/single-step-backtrack.md`.

To be clear about what this is and isn't: this is not PubGrub. It is
not even a complete SAT-style solver. It is the smallest amount of
backtracking that handles the diamond cases users actually file
issues about, with a runtime bound that is still linear in graph size
in the no-conflict case. We chose it because it ships in a 1.1 instead
of a 1.5, and because the diagnostic improvements (which work whether
or not backtracking succeeds) are valuable on their own.

The v1.2 milestone targets actual PubGrub integration. That is a much
larger change — different data structures, different conflict
representation, real incompatibility tracking — and it is properly a
project unto itself. 1.1 is the half-step that buys us most of the
practical benefit while we build it.

## Known limitations

Things that 1.1 does not do, and that we know users will ask about:

Aliases don't work in `peerDependencies` or `optionalDependencies`
yet. The manifest parser accepts the `npm:` syntax in those fields,
but the resolver does not yet propagate the aliased name through the
peer/optional code paths. This will land in a 1.x. For now, aliases
are restricted to `dependencies` and `devDependencies`.

Aliases pointing at `file:` or `git+` specs aren't supported. Only
`npm:<name>@<spec>` is recognized. We want to think a little more
about how a `git:` alias should interact with the lockfile's git
resolution machinery before committing to a syntax.

Path-keyed overrides don't support wildcards. You can write
`"a > b > c"` but not `"a > * > c"`. Wildcards in path keys are on
the v1.2 list; they require a small extension to the override matcher
that we wanted to design alongside the richer glob support below
rather than ship piecemeal.

Glob resolutions only support the `**/<name>` shape. Patterns like
`pkg/**/foo`, `*-helper`, or `prefix-*/leaf` parse without error but
do not match anything. This matches yarn's documented behavior for
the same patterns, which we copied deliberately so manifests are
portable, but we know users want more. Richer glob support is on the
1.2 milestone.

The resolver still doesn't backtrack across multiple levels. If your
graph requires unwinding two or more ancestor choices to find a
solution, the install will still error. The full PubGrub work in 1.2
is the right place to fix this; we explicitly chose not to grow the
single-step algorithm into a multi-step one, because at that point
you are reinventing PubGrub badly.

## What's coming in v1.2

The 1.2 milestone is shaping up around three themes:

- **Full PubGrub integration.** Replace the single-step backtracker
  with a real PubGrub-style solver. Better conflict diagnostics, real
  incompatibility tracking, and a search strategy that handles the
  multi-level cases 1.1 doesn't.
- **Workspace inter-dep linking.** Promoted from the 1.3 milestone.
  Workspaces in 1.0/1.1 resolve as separate roots that happen to share
  a lockfile; 1.2 will let workspace packages link to each other
  symbolically without round-tripping through the registry, the way
  yarn workspaces and pnpm workspaces both do.
- **Richer glob support.** Patterns like `pkg/**/foo`, `*-helper`, and
  prefix/suffix matchers in both `resolutions` and path-keyed
  overrides. Pushed forward from the 1.3 milestone now that the
  matcher infrastructure is closer to landing.

As always, the milestone list on the issue tracker is the
authoritative version; this section is the editorial summary.

## How to upgrade

For most users, upgrading from 1.0 to 1.1 is `cargo install
guroku --version ^1.1` (or the equivalent for your install method)
and you are done. The CLI is unchanged, the lockfile is forward-
compatible, and the new features are opt-in via manifest fields you
weren't using before.

For library consumers — anyone calling `guroku-core` directly from
Rust — there is a short list of mechanical changes (the
`#[non_exhaustive]` arm, the `aliased_from: None`, the
`requested_by` parse update). The full step-by-step migration guide,
including a checklist and example diffs, is at
`docs/migration/v1.0-to-v1.1.md`.
