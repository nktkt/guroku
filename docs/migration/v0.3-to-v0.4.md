# Migrating from guroku v0.3 to v0.4

This guide walks through what changed between v0.3 and v0.4, what you need
to do (if anything), and how to roll back if v0.4 doesn't work for you.

## 1. Why migrate

v0.4 is the first guroku release that runs lifecycle scripts the way npm
and pnpm do. Concretely, you get:

- Automatic `preinstall`, `install`, `postinstall`, and `prepare` hooks.
- Two new subcommands: `guroku run` and `guroku exec`.
- `.npmrc` reading for registry overrides (project-local and user-global).
- `node_modules/.bin/` shims for the bin entries of your direct deps.

There are **no on-disk format changes** from v0.3. The CAS layout under
`~/.guroku/cas/`, the `node_modules` tree, and the lockfile schema are all
identical. You can keep your existing store and lockfile as-is.

## 2. What's new

- **Lifecycle scripts** (`preinstall`, `install`, `postinstall`, `prepare`)
  are now run automatically during `guroku install`, in dependency order.
- **`--ignore-scripts`** flag for `guroku install` to skip all lifecycle
  scripts (both root and per-dep).
- **`guroku run [<script>] [-- <args>]`** runs a script from your
  manifest's `scripts` field, with `node_modules/.bin` prepended to PATH.
  With no script name, it lists available scripts.
- **`guroku exec <cmd> [args...]`** runs an arbitrary command with
  `node_modules/.bin` prepended to PATH.
- **`guroku workspaces`** lists the workspace packages discovered from
  the root manifest's `workspaces` globs.
- **`node_modules/.bin/`** is now populated with symlinks to the bin
  entries declared by your direct dependencies.
- **`.npmrc`** is read from the project root and from the user's home
  directory. The project file overrides the user file. Currently the
  `registry=` key and scoped `@scope:registry=` keys are honoured.
- **New error variants**: `ScriptFailed`, `ScriptSpawnFailed`,
  `NoSuchScript`, `BinNotFound`, `WorkspaceMisconfigured`. If you match
  on the public error enum in your own code, add arms for these.
- **New library API**:
    - `RegistryClient::from_npmrc` constructs a client from a parsed
      `.npmrc` config.
    - `Manifest::bin_entries` and `Manifest::workspace_globs` expose the
      newly typed fields.
    - The `npmrc` module: parser and merge helpers.
    - The `scripts` module: `run_script`, `run_lifecycle`, env setup.
    - The `workspaces` module: glob expansion and package discovery.
    - `linker::populate_bin_dir` writes the `.bin/` symlinks.

## 3. Behaviour changes that may affect you

### Lifecycle scripts run by default

In v0.3, guroku silently ignored `preinstall`/`install`/`postinstall`/
`prepare` in dep manifests. In v0.4 they run. If your project has deps
whose `postinstall` works under npm but was a no-op under v0.3, those
scripts will now execute on `guroku install`.

If you don't want that, pass `--ignore-scripts`:

```sh
guroku install --ignore-scripts
```

You can also set it once for CI; see section 6.

### Bin script mode bumped to 0o755

When guroku links a dep's bin entry into `node_modules/.bin/`, it
ensures the target file at `node_modules/<name>/<bin-script>` is
executable. If the file's current mode is missing the user-execute
bit, guroku will `chmod` it to `0o755`. This is the same behaviour npm
and pnpm have had for years; it's only new for guroku.

If you have tooling that asserts on exact file modes inside
`node_modules`, you may see a diff.

### Manifest now has typed fields

In v0.3, `scripts`, `bin`, and `workspaces` all fell through to
`Manifest::other` (a `serde_json::Value` catch-all). In v0.4 they are
first-class fields:

```rust
pub struct Manifest {
    pub name: String,
    pub version: Version,
    pub dependencies: BTreeMap<String, VersionReq>,
    pub dev_dependencies: BTreeMap<String, VersionReq>,
    pub scripts: BTreeMap<String, String>,
    pub bin: Option<BinField>,
    pub workspaces: Option<Vec<String>>,
    pub other: serde_json::Value,
}
```

If your code serialises a v0.4 `Manifest` back to JSON, those fields
will appear at the top level rather than inside `other`. The on-disk
`package.json` shape doesn't change; only the in-memory representation
and any JSON round-trip you do yourself.

## 4. What didn't change

- **Store layout**: `~/.guroku/cas/` is byte-for-byte compatible. v0.4
  reads and writes the same content-addressed blobs.
- **`node_modules` layout**: still strict, pnpm-style (each package in
  its own directory under `node_modules/.guroku/<name>@<ver>/` with the
  top level only containing direct deps).
- **Lockfile schema**: `guroku.lock` from v0.3 is read by v0.4 without
  migration. v0.4 writes the same schema.
- **CLI surface for `install`/`add`/`remove`**: same flags and same
  semantics, with the single addition of `--ignore-scripts` on
  `install`.

## 5. First-run checklist

1. Build or install the v0.4 binary.
2. Run `guroku install` once in your project. Watch the output for
   `[preinstall]` and `[postinstall]` lines from your deps. If
   something fails noisily, see section 8.
3. (Optional) If you publish to or pull from a private registry, drop
   a `.npmrc` at the project root:

    ```
    registry=https://npm.example.com/
    @myscope:registry=https://npm.example.com/
    ```

4. (Optional) Replace `npm run <script>` calls in your dev workflow
   with `guroku run <script>`. The PATH setup is equivalent.

## 6. CI considerations

For untrusted dependency trees (the common case), use:

```sh
guroku install --frozen-lockfile --ignore-scripts
```

This pins resolution to the lockfile and skips all lifecycle scripts,
which is the safest default for CI.

For CI you trust to run third-party scripts (e.g. you've audited your
deps, or you need `node-gyp`-style native builds to happen):

```sh
guroku install --frozen-lockfile
```

If you previously ran `npm ci` in CI and expect postinstalls to fire,
plain `--frozen-lockfile` is the closer match.

## 7. Reverting

If v0.4 misbehaves for you, you can drop back to v0.3 cleanly:

1. Reinstall the v0.3 binary.
2. Re-run `guroku install`.

There is no on-disk migration to undo. v0.3 ignores the new typed
fields on `Manifest` (`scripts`, `bin`, `workspaces`) by treating them
as unknown JSON keys, which fall through to `manifest.other`. The
lockfile and CAS store are unchanged across versions.

The only thing v0.3 won't reproduce is the `node_modules/.bin/`
directory; you can either run direct binaries via their full path
under `node_modules/<pkg>/...` or use `npx`/`npm exec` against the
same tree.

## 8. Common errors and fixes

### `script "postinstall" exited with status 1`

A dependency's `postinstall` ran and failed. v0.4 demotes per-package
`postinstall` failures to warnings by default, so the install as a
whole still succeeds; the failing package is left on disk and the
warning is printed to stderr. A failure in your **root** project's
`postinstall` does abort the install.

What to do:

- If it's a root-level script: fix the script. Read the stderr above
  the error line.
- If it's a dep and you don't care: ignore the warning, or rerun with
  `--ignore-scripts` if you want a clean log.
- If it's a dep and you do care (e.g. it builds a native addon you
  need): reproduce it manually with
  `cd node_modules/<pkg> && npm run postinstall` to see the full
  output, then file the issue upstream.

### `<name> is not on PATH and was not found in node_modules/.bin`

You ran `guroku exec <name>` (or a `guroku run` script that calls
`<name>`), but `<name>` isn't installed and isn't on your shell PATH.

What to do:

- Add the package: `guroku add <name>` (or `--save-dev`).
- Or check that the package you expect to provide that bin actually
  declares it in its `bin` field.
- Or use the absolute path if it's a system tool that's on PATH for
  your shell but not for the subprocess (rare; usually a PATH
  inheritance issue in your shell config).

### Slow first install after upgrading

The first `guroku install` after upgrading to v0.4 may feel slower
than v0.3 did, because lifecycle scripts now run. If you're iterating
on `package.json` and don't need the postinstalls each time:

```sh
guroku install --ignore-scripts
```

Then run a full install (without the flag) once before you ship.

---

That's it. For most projects the upgrade is "install the new binary
and run `guroku install`". The script-running behaviour is the only
change you're likely to notice in day-to-day use.
