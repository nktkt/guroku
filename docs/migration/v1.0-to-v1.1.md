# Migration guide: guroku v1.0 to v1.1

This guide walks you through upgrading from guroku v1.0 to v1.1. v1.1 is a
backwards-compatible release: existing projects keep working without any
configuration changes, and the on-disk store, lockfile schema, and
node_modules layout are all unchanged.

## 1. Why migrate

v1.1 expands what your existing `package.json` can express, without breaking
anything you already have. The headline additions are three new manifest
features and one resolver improvement.

- **npm aliases.** A dependency entry whose value starts with `npm:` is now
  understood as an alias. The key is the local name you import; the value
  points at the real package and version range.

  ```json
  {
    "dependencies": {
      "lodash-4": "npm:lodash@^4",
      "lodash-3": "npm:lodash@^3"
    }
  }
  ```

  This lets you depend on two majors of the same package without forking
  either of them.

- **Path-keyed overrides.** The `overrides` block now accepts keys that
  describe a contiguous chain through the dependency graph, separated by
  ` > `. The override applies only when the resolver is walking that exact
  chain.

  ```json
  {
    "overrides": {
      "a > b > c": "1.0.0"
    }
  }
  ```

  Use this when a flat name override would be too broad (it would pin every
  copy of `c` everywhere) and you only want to pin the copy that comes in
  through `a` then `b`.

- **Glob resolutions.** Keys may now contain `*` and `**` segments. `**`
  matches any chain (including empty); `*` matches a single segment. This
  is similar in spirit to yarn's `resolutions` field.

  ```json
  {
    "overrides": {
      "**/foo": "1.0.0",
      "react-* > scheduler": "0.23.0"
    }
  }
  ```

- **Resolver upgrade: single-step backtracking on diamond conflicts.**
  When two parents demand incompatible ranges of the same dependency, the
  v1.0 resolver would error. v1.1 will first try to relax the most recently
  picked version of either parent by one step (the next compatible version
  that still satisfies its own requesters) before giving up. Diamonds that
  used to error often now resolve cleanly.

If none of these features interest you, you can still upgrade: v1.1 is
backwards-compatible at the manifest, lockfile, and CLI level.

## 2. What's new

API surface added in v1.1, by module:

- `guroku::specs::DepSpec` gains a new variant:

  ```rust
  pub enum DepSpec {
      Version(VersionReq),
      Path(PathBuf),
      Git(GitSpec),
      Alias { real_name: String, inner: Box<DepSpec> },
  }
  ```

  The `inner` field holds whatever the alias resolves to (almost always a
  `Version`, but the type allows any `DepSpec`).

- `DepSpec` is now `#[non_exhaustive]`. External `match` blocks must
  include a wildcard arm. (See section 3.)

- `guroku::overrides::lookup_with_path(manifest, path)` is the new
  preferred entry point. `path` is a slice of dependency names describing
  where you are in the resolution graph; the function returns the
  highest-precedence override that applies. The v1.0 entry point,
  `lookup(manifest, name)`, still works for flat-name lookups but does
  not see path-keyed or glob overrides.

- `guroku::overrides::classify_entries(manifest)` returns a structured
  diagnostic of each override entry: which are flat, which are
  path-keyed, which are globs, and which (if any) are unparseable. Useful
  for `guroku doctor` style tooling.

- `guroku::resolver::resolve_with_manifest_overrides(manifest, registry)`
  is the new public entry point that respects path-keyed and glob
  overrides. The v1.0 entry points (`resolve` and
  `resolve_with_overrides`) are retained for source compatibility but
  only honour flat-name overrides.

- `guroku::resolver::Resolved` gains a field:

  ```rust
  pub struct Resolved {
      pub name: String,
      pub version: Version,
      pub source: Source,
      pub aliased_from: Option<String>,
      // ...
  }
  ```

  `aliased_from` is `Some(local_name)` when the entry was reached through
  an npm alias (where `local_name` is the key in your `dependencies`),
  and `None` otherwise.

- `ResolutionConflict.requested_by` is now a path string formatted as
  `"a > b > c"` instead of just the immediate parent's name. This is the
  same path you would pass to `lookup_with_path`.

## 3. Behaviour changes that may affect you

These are the only places v1.1 may behave differently from v1.0.

### Library API

External `match` blocks on `DepSpec` must add a `_` arm, because
`DepSpec` is now `#[non_exhaustive]`. For most consumers this is the same
forward-compat treatment that already applies to `GurokuError`, so the
fix is mechanical.

```rust
match spec {
    DepSpec::Version(req) => { /* ... */ }
    DepSpec::Path(p) => { /* ... */ }
    DepSpec::Git(g) => { /* ... */ }
    _ => { /* handle Alias and any future variants */ }
}
```

If you build `Resolved` values yourself (for example, in tests or in a
custom registry adapter), you need to populate the new `aliased_from`
field. `None` is correct for any entry that did not come from an alias.

### Resolver

Diamond conflicts that v1.0 would have errored on may now succeed. The
new single-step backtracking is conservative: it only relaxes the most
recently picked version, and only when there is a clearly-compatible
alternative. Concretely:

- If you are CI-locking with `--frozen-lockfile`, **no change** — the
  resolver runs from the lockfile and never backtracks.
- If you regenerate the lockfile (`guroku install` with no lockfile, or
  `guroku update`), you may see different (better) version picks for
  packages that previously errored out and required a manual override.

If you previously worked around a diamond by adding a flat override, the
override still wins. v1.1 only kicks in when there is no override.

### Conflict messages

`ResolutionConflict.requested_by` shape changed from `"<parent-name>"`
to `"<chain> > <of> > <names>"`. If you have code or scripts that parse
this field — for example, a CI bot that posts conflict comments — they
need updating.

```text
v1.0: requested_by: "webpack"
v1.1: requested_by: "my-app > webpack"
```

The leading element is the root package; the trailing element is the
direct parent of the conflicting dependency.

## 4. What didn't change

These are explicit non-changes; if you were relying on any of them,
nothing breaks.

- **On-disk store / CAS layout.** Same hash-addressed layout under the
  store root. v1.1 reads and writes the v1.0 store as-is.
- **Strict node_modules layout.** Same shape. No flattening, no hoisting
  changes.
- **Lockfile schema.** Still `lockfileVersion: 1`. v1.1 reads and writes
  v1.0 lockfiles. (Aliased entries serialise with their local name as
  the key, exactly as in v1.0; the alias relationship is reconstructible
  from the manifest.)
- **All other CLI subcommands and flags.** `install`, `add`, `remove`,
  `update`, `run`, `exec`, `doctor`, `cache`, `store` — all behave
  identically.
- **Manifest schema.** The manifest is still the same `package.json` you
  already use. Alias entries are just strings in `dependencies`;
  path-keyed and glob entries are just strings in `overrides`. No new
  top-level fields.

## 5. First-run checklist

Upgrading is intentionally boring.

1. Build or install v1.1.

   ```sh
   cargo install --locked --version 1.1.0 guroku
   # or, from source:
   git checkout v1.1.0
   cargo build --release
   ```

2. Run your existing project's `guroku install`. No config changes are
   required. The lockfile is honoured if present; otherwise a fresh
   resolution runs and benefits from the new backtracking.

   ```sh
   cd path/to/your/project
   guroku install
   ```

3. (Optional) Take advantage of new features as the need arises:

   - **Add an alias entry** if you've been duplicating a package under a
     different name. Replace the duplicate with an `npm:` entry.

     ```json
     {
       "dependencies": {
         "lodash-4": "npm:lodash@^4"
       }
     }
     ```

   - **Replace a flat override with a path-keyed one** if it was
     over-broad. Flat overrides pin every copy of a name; path-keyed
     overrides pin only the copy reached via a specific chain.

     ```json
     {
       "overrides": {
         "a > b > c": "1.0.0"
       }
     }
     ```

   - **Add a glob resolution** if you have a yarn-style `resolutions`
     you've been postponing. `**/foo` pins every transitive copy of
     `foo`; `parent-* > foo` pins copies under any `parent-*`.

     ```json
     {
       "overrides": {
         "**/foo": "1.0.0"
       }
     }
     ```

There is no migration command. There is nothing to convert.

## 6. For library consumers

If you depend on `guroku` as a Rust crate, here is the short list of
mechanical changes.

- Add `_ => ...` arms to every `match DepSpec`. Same forward-compat
  treatment you already apply to `GurokuError`.

  ```rust
  let summary = match spec {
      DepSpec::Version(_) => "version",
      DepSpec::Path(_) => "path",
      DepSpec::Git(_) => "git",
      _ => "other",
  };
  ```

- Switch to `resolver::resolve_with_manifest_overrides` to get
  path-keyed and glob support. The old `resolve` and
  `resolve_with_overrides` still compile and run; they just don't honour
  the new override forms.

  ```rust
  use guroku::resolver;

  let graph = resolver::resolve_with_manifest_overrides(&manifest, &registry)?;
  ```

- Read `Resolved::aliased_from` to detect alias-resolved entries. If
  your tool prints, links, or hashes resolved entries, decide whether
  you want to surface the alias name, the real name, or both.

  ```rust
  for entry in &graph.entries {
      match &entry.aliased_from {
          Some(local) => println!("{} (alias of {})", local, entry.name),
          None => println!("{}", entry.name),
      }
  }
  ```

- If you build `Resolved` values directly (tests, custom adapters), add
  `aliased_from: None` (or the appropriate `Some`) to your literals.

## 7. Reverting

If something goes wrong, reverting is straightforward.

1. Install the v1.0 binary.

   ```sh
   cargo install --locked --version 1.0.3 guroku
   ```

2. Run `guroku install`. The lockfile is unchanged across the upgrade,
   so v1.0 loads it fine and reproduces the same node_modules tree.

If you started using path-keyed or glob overrides, v1.0 will silently
ignore them. The keys land in the in-memory map, but v1.0's
`overrides::lookup` only checks flat names, so the entries are inert.
You will not get an error; you will just not get the override applied.
If that matters to your build, remove the new-style entries before
downgrading.

Aliased dependency entries (`"my-name": "npm:real@^1"`) are not
understood by v1.0 — the v1.0 manifest parser will reject the entry. If
you have alias entries and need to downgrade, remove them and replace
with the duplicated form you would have used pre-v1.1.

## 8. Common errors and fixes

A short list of things you may run into and how to resolve them.

- **`match` not exhaustive on `DepSpec`.** Add a `_` arm. This is the
  most common library-side error after upgrading.

  ```rust
  match spec {
      DepSpec::Version(_) => { /* ... */ }
      DepSpec::Path(_) => { /* ... */ }
      DepSpec::Git(_) => { /* ... */ }
      _ => { /* ... */ }
  }
  ```

- **`expected struct field `aliased_from`` / "missing field
  `aliased_from`".** v1.1 added the field to `Resolved`. Library
  consumers that build `Resolved` literals (typically in tests) need to
  add `aliased_from: None` (or `Some("...")` where appropriate).

  ```rust
  Resolved {
      name: "foo".into(),
      version: "1.2.3".parse().unwrap(),
      source: Source::Registry,
      aliased_from: None,
  }
  ```

- **Path-keyed override didn't apply.** Confirm the path is a contiguous
  suffix of the chain you actually resolve through. `"a > b > c"`
  matches when the resolver is at `c` reached via `b` reached via `a`,
  in that order, with no other names in between. Check
  `lookup_with_path` precedence: more specific keys win, with flat keys
  as the lowest-precedence fallback. Use
  `overrides::classify_entries` to confirm your entry parsed as
  path-keyed and not as flat.

  ```sh
  guroku doctor --overrides
  ```

- **Conflict bot posts garbled parent names.** Your bot is parsing the
  v1.0 shape of `requested_by`. Update it to split on ` > ` and take
  the last segment if you want the immediate parent, or the first
  segment if you want the root package.

- **Diamond resolution picks a different version after upgrade.** This
  is the new backtracking doing its job. If you want the old behaviour,
  add a flat or path-keyed override that pins the version you want;
  overrides take precedence over the resolver's choice.
