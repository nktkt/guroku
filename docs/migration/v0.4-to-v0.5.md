# Migrating from guroku v0.4 to v0.5

This guide covers what changed between v0.4 and v0.5, what to check on
existing projects, and how to roll back if you need to.

## 1. Why migrate

v0.5 is the release that unblocks the day-to-day workflows that v0.4 could
not actually serve in private environments. In particular:

- **Private registries** now work end-to-end. `_authToken` entries in
  `.npmrc` are wired through every outgoing HTTP request, so authenticated
  fetches finally succeed.
- **`file:` dependencies** install cleanly via local-source linking instead
  of erroring out.
- **`git+` dependencies** (including `github:user/repo` shorthands) install
  via a subprocess `git clone` into the on-disk cache.
- **`package.json#overrides`** and **`resolutions`** are honoured for
  transitive version pinning, so you can patch a vulnerable transitive dep
  without forking.
- **`guroku audit`** queries the registry's advisory DB and reports
  vulnerabilities.

There are **no on-disk format changes**. The CAS layout, the strict
`node_modules/.guroku/` layout, and the lockfile schema are all unchanged
from v0.4. Upgrading and downgrading is a binary swap.

## 2. What's new

- `_authToken` from `.npmrc` is now sent on outgoing HTTP. v0.4 parsed
  these entries but silently dropped them on the floor.
- `<scope>:registry=` actually routes scoped fetches. Previously every
  fetch went to the default registry regardless of scope config.
- `file:./path` deps install via local-source linking. The path is
  resolved relative to the consuming `package.json`.
- `git+https://...` (and the `github:`, `gitlab:`, `bitbucket:` shorthands)
  install via subprocess `git clone` into `~/.guroku/cache/git/`,
  keyed by repo URL and resolved commit.
- `package.json#overrides` and `resolutions` are honoured for transitive
  version pinning. Both fields are accepted; `overrides` wins on conflict.
- `guroku audit` queries the registry's advisory DB
  (`/-/npm/v1/security/advisories/bulk`) and prints findings grouped by
  severity.
- New error variants: `FileDepMissingManifest`, `GitCommandFailed`,
  `AuditFailed`, `InvalidOverride`. These bubble up through the existing
  `GurokuError` enum, so any code matching `_` still compiles.
- `RegistryClient::from_npmrc` now wires npmrc through every outgoing
  request. If you construct a client manually, prefer this constructor
  over `RegistryClient::new`.

## 3. Behaviour changes that may affect you

Read this section even if your project "just works" after the upgrade.

- **Stale `_authToken` entries are now sent.** If your `.npmrc` has an
  `_authToken` left over from a previous setup, v0.5 will start sending
  it on requests to whatever registry it is keyed to. Audit your
  `.npmrc` (both `~/.npmrc` and any in-tree ones) for stale tokens, and
  rotate any that may have leaked. v0.4 was inadvertently protecting you
  here by ignoring them.
- **Scoped fetches now route to the scope's registry.** If you set
  `@scope:registry=` in `.npmrc` long ago but never tested it (because
  v0.4 ignored it), you may now discover misconfiguration. Symptoms:
  unexpected `404`s, or `401`s if the scope's registry requires auth and
  your token is keyed to a different host.
- **`file:./path` deps that previously errored now install.** If you
  built a workaround that depended on the v0.4 error (for example, a
  build script that catches the failure and runs a manual symlink),
  remove it. The workaround will either be a no-op or actively
  conflict.
- **`git+` deps now require the `git` binary on `PATH`.** v0.5 shells
  out; there is no in-process git client. If `git` is missing, you will
  see `GitCommandFailed`. CI images that strip `git` after checkout will
  need to keep it installed.

## 4. What didn't change

- The on-disk store and CAS layout. Existing CAS contents from v0.4 are
  reused as-is.
- The strict `node_modules/.guroku/` layout, including peer-dep
  specialisation suffixes.
- The lockfile schema. v0.4 lockfiles are read by v0.5 without
  migration, and v0.5 lockfiles are read by v0.4 (the new fields fall
  through to `manifest.other`).
- The CLI surface for `install`, `add`, `remove`, `run`, `exec`, and
  `workspaces`. No flags were removed or renamed.

## 5. First-run checklist

1. Build/install v0.5 (`cargo install --path . --locked`, or whichever
   distribution you use).
2. (Optional) Add `.npmrc` with private-registry config if you have one.
   If you already have an `.npmrc`, audit it now per section 3 before
   running anything.
3. (Optional) Use `file:./path` for in-house libs you used to symlink
   manually. Delete the manual symlinks first or `guroku install` will
   fight them.
4. (Optional) Run `guroku audit` against an existing project; add
   `overrides` for any high or critical findings, then re-run `guroku
   install` to lock the override in.

## 6. CI

If your CI hits a private registry, write `~/.npmrc` before `guroku
install`. A typical GitHub Actions job step looks like:

```yaml
- run: echo "//npm.acme.internal/:_authToken=${{ secrets.NPM_TOKEN }}" >> ~/.npmrc
- run: guroku install --frozen-lockfile --ignore-scripts
- run: guroku audit
```

Notes:

- `--frozen-lockfile` keeps CI honest about lockfile drift.
- `--ignore-scripts` is the recommended default for CI; lifecycle scripts
  from third-party packages should not run with your registry token in
  the environment.
- `guroku audit` exits non-zero on high/critical findings by default. If
  you want CI to surface findings without failing, run it with
  `--exit-zero` and parse the JSON output.

A scheduled audit workflow is provided at
`.github/workflows/audit-cron.yml`. Drop it in as-is for a daily run, or
adjust the cron expression to taste. It runs `guroku audit` against the
default branch and opens an issue if anything new shows up.

## 7. Reverting

If v0.5 misbehaves on your project, you can downgrade with no data
migration:

1. Install the v0.4 binary.
2. Run `guroku install` as normal.

The new fields in `Manifest` (`overrides`, `resolutions`) just fall
through to `manifest.other` in v0.4, so the lockfile and CAS produced
by v0.5 are readable by v0.4. v0.4 will simply ignore your `_authToken`
settings (it won't send them), which means private-registry fetches
will go back to failing - that's expected, and is the bug v0.5 fixes.

You do not need to delete `node_modules/`, the lockfile, or
`~/.guroku/`. The CAS layout is unchanged.

## 8. Common errors and fixes

- **`audit request failed: HTTP 404`** - your registry doesn't proxy
  `/-/npm/v1/security/advisories/bulk`. Most private registry products
  do not implement the advisory endpoint. Point `guroku audit` at
  `npm.com` (or whichever public registry mirrors the advisory DB) for
  the audit step, even if your installs go through a private registry.
- **`git command failed for <url>: fatal: ... terminal prompts
  disabled`** - `git+` cloning a private repo failed because git tried
  to prompt for credentials. Set up git's credential helper, or use SSH
  keys (`git+ssh://...`) and an SSH agent. guroku does not pass
  credentials to git itself.
- **`file dependency at './pkg' has no readable package.json`** - fix
  the path. Remember it's resolved **relative to the consuming
  `package.json`**, not relative to the working directory of the
  `guroku` invocation. A `file:./pkg` in a workspace package looks for
  `<workspace-pkg-dir>/pkg/package.json`.
- **`401 Unauthorized` on a private registry** - token typo, or the
  `//host/` prefix in your `.npmrc` doesn't match the registry URL
  exactly. The match is literal: include the port if the registry URL
  has one (`//npm.acme.internal:8443/:_authToken=...`), and include the
  trailing slash. Double-check against the URL printed in the error
  message.

If you hit something that isn't covered here, please file an issue with
the output of `guroku --version` and the command you ran.
