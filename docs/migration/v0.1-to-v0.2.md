# Migrating from guroku v0.1 to v0.2

This guide covers what changed between guroku v0.1 and v0.2, what you need to
do to upgrade, and how to back out if something goes wrong.

## 1. Why migrate

v0.1 had a resolver that only understood literal versions. Anything fancier
than `1.2.3` -- a caret, a tilde, a range, an `x`, a union -- was not really
parsed. The client silently fell back to whatever the registry called
`latest`. That meant the package you got often had nothing to do with the
spec you wrote in `package.json`.

v0.2 actually parses semver ranges and picks the highest matching published
version. This is a correctness fix, not a new feature. The cost is that
specs which used to "work" by accident may now resolve to a different
version, or fail outright.

If your project pins everything to exact versions, the upgrade is a no-op.
If you use ranges, read on.

## 2. What changed

- Range specs now resolve correctly. The supported syntaxes are the usual
  npm ones:
  - caret: `^1.2.3`
  - tilde: `~1.0`
  - explicit comparator sets: `>=1 <2`
  - x-ranges: `1.x`, `1.2.x`
  - unions: `^1 || ^2`
- `guroku.lock` is now written on every install. Commit it. The format is
  versioned (currently `v1`); future guroku releases may bump it.
- A new flag, `guroku install --frozen-lockfile`, fails the install if the
  lockfile would need to be regenerated. Use this in CI.
- `package.json` `peerDependencies` and `optionalDependencies` are now read
  and round-tripped through the in-memory `Manifest`. They are **not**
  installed yet -- this just means guroku no longer drops them when it
  rewrites the manifest.

## 3. Behaviour changes that may break you

### Unsatisfiable ranges are now errors

A spec like `^99` against a registry that has no `99.x` published will fail
with `no matching version for X@^99` instead of silently installing the
registry's `latest`. This is the headline correctness fix and it is the
most likely thing to bite you.

**Action:** pin to a real range that resolves, or remove the dep.

### `install` grew a flag

`guroku install` accepts `--frozen-lockfile`. If you parse `guroku --help`
output in a script (please don't, but people do), the help text has changed
and your parser may need updating. The exit codes and the default behaviour
of `install` with no flags are unchanged.

### `RegistryClient::default` was renamed

Lib API consumers only. The associated function

```rust
RegistryClient::default()
```

has been renamed to

```rust
RegistryClient::with_default_registry()
```

to satisfy `clippy::should_implement_trait`. `RegistryClient` does not
implement the `Default` trait and the old name was misleading. The new name
is the only change; the body is identical.

If you import guroku as a library, this is a one-line fix at each call
site. If you only use the CLI, you will not notice.

## 4. What didn't change

- `node_modules` layout is still a flat copy of every package. The
  content-addressable store and hardlink-based linker are scheduled for
  v0.3.
- Lifecycle scripts (`preinstall`, `install`, `postinstall`, etc.) still do
  not run. If your project depends on them, guroku is not yet a drop-in
  replacement for npm/pnpm.
- The public Rust API of these items is unchanged from v0.1:
  - `Manifest`
  - `RegistryClient` (apart from the `default` rename above)
  - `tarball::extract`
  - `linker::link_flat`
  - `cache::*`

If you were using these from another crate, you should not need to touch
your code beyond the `default` rename.

## 5. First-run checklist

1. Install the v0.2 binary:

   ```sh
   cargo install --git https://github.com/nktkt/guroku --tag v0.2.0
   ```

   or build from source if you prefer.

2. `cd` into your project.

3. Delete the existing `node_modules/`. Optional but recommended -- it
   guarantees you are looking at what v0.2 actually resolves, not whatever
   v0.1 left behind.

   ```sh
   rm -rf node_modules
   ```

4. Run `guroku install` once. This resolves your ranges, downloads any
   missing tarballs, populates `node_modules/`, and writes `guroku.lock`.

   ```sh
   guroku install
   ```

5. Commit `guroku.lock`.

   ```sh
   git add guroku.lock
   git commit -m "Add guroku v0.2 lockfile"
   ```

6. In CI, switch to the frozen variant so a drifting lockfile fails the
   build instead of being silently regenerated:

   ```sh
   guroku install --frozen-lockfile
   ```

## 6. Reverting

To roll back to v0.1:

1. Keep your `package.json` as-is.
2. Delete `guroku.lock`. v0.1 does not understand it and will not benefit
   from it.
3. Reinstall the v0.1 binary (whatever method you used originally; the
   `cargo install` line above takes a `--tag v0.1.0` instead).

v0.1 ignores any unrecognised file in your project, so leaving the lockfile
in place is harmless if you would rather not delete it -- but it will go
stale.

## 7. Common errors and fixes

### `no matching version for X@^Y`

Your spec resolves to nothing. Either no version exists, or the published
versions all sit outside your range. Widen the range, pick an exact
version that exists, or drop the dependency.

### `lockfile is out of date with package.json`

You ran `guroku install --frozen-lockfile` after editing `package.json`
without regenerating the lockfile. Drop the flag once:

```sh
guroku install
git add guroku.lock
```

then re-add `--frozen-lockfile` for CI.

### `lockfile version mismatch: file is v2, this guroku understands v1`

You ran a newer guroku in this project at some point, which upgraded the
lockfile, and you are now trying to use v0.2. Either upgrade guroku to the
version that produced the lockfile, or delete `guroku.lock` and let v0.2
regenerate it at v1.

## 8. Where to file issues

Bugs, surprises, and resolver edge cases:
<https://github.com/nktkt/guroku/issues>

v0.2 is the first release with a real range resolver, so resolver bugs are
expected. A reproduction with the exact spec, the registry response (or
just the package name and version range), and the guroku version is the
most useful thing you can attach.
