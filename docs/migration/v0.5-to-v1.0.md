# Migrating from guroku v0.5 to v1.0

This guide covers what changed between v0.5 and v1.0, what to check on
existing projects, and how to roll back if you need to.

## 1. Why migrate

v1.0 is the first release with a stability commitment. Specifically:

- The **lockfile format** is now SemVer-covered. A v1.0 lockfile written
  by guroku v1.x will continue to be readable by every guroku v1.x.
- The **public Rust API** is now SemVer-covered. The crate-root
  re-exports, the new `guroku::prelude` module, and the surface listed
  in section 6 will not break compatibly within the v1.x line.

That's it. There are **no new features** beyond the formalisation of
the existing surface, no on-disk format changes, and no resolver
changes. If your v0.5 setup works today, your v1.0 setup will work
tomorrow without code or config edits.

## 2. What's new

The additions in v1.0 are documentation, scaffolding, and release-side
changes. They do not affect runtime behaviour.

- **Comprehensive crate-level rustdoc.** The crate root now has a
  full module-level overview, with worked embedding examples that
  compile under `cargo test --doc`. If you embed guroku as a library,
  start at `cargo doc --open -p guroku`.
- **`guroku::prelude`.** A new module that re-exports the recommended
  embedding surface in one place. See section 6 for the contents and
  the recommended usage.
- **`GurokuError` is now `#[non_exhaustive]`.** Future variants can be
  added in a v1.x minor release without breaking downstream `match`
  expressions, as long as those `match`es include a `_` arm. This is
  the only library-side behaviour change in v1.0; see section 3.
- **Windows release binaries.** The release workflow now produces
  prebuilt binaries for `x86_64-pc-windows-msvc` and
  `aarch64-pc-windows-msvc` alongside the existing Linux and macOS
  targets. Source builds on Windows already worked in v0.5; v1.0 just
  ships official artifacts.
- **Criterion benchmark scaffolding.** A `benches/` directory is now
  part of the repo, wired through Criterion. This is for contributors
  and downstream forks; it doesn't ship in the published binaries and
  isn't part of the stable API.

## 3. Behaviour changes that may affect you

Read this section even if your project "just works" after the upgrade.
The list is short.

- **Library API: `GurokuError` is `#[non_exhaustive]`.** If you
  `match` on `GurokuError` exhaustively (one arm per variant, no `_`),
  `cargo build` will now fail with `non-exhaustive patterns`. Add a
  `_ => ...` arm. This was always the idiomatic shape for matching on
  a foreign error enum; v1.0 enforces it via the attribute so that
  v1.x can add new variants without a breaking release. The fix is
  one line.
- **CLI: no breaking changes.** Every flag and subcommand from v0.5
  is preserved verbatim. `guroku install`, `add`, `remove`, `run`,
  `exec`, `workspaces`, and `audit` all behave the same. Exit codes
  and human-readable messages are unchanged from v0.5 and are now
  documented as stable; see `docs/cli-reference.md` and
  `docs/error-codes.md`.
- **Lockfile: no schema change.** v0.5 lockfiles load on v1.0 without
  migration. v1.0 lockfiles also load on v0.5, since v1.0 doesn't add
  any fields. The schema is now SemVer-covered; v1.x may add optional
  fields, but won't remove or repurpose existing ones.
- **On-disk store: unchanged.** The CAS layout under `~/.guroku/` and
  the strict `node_modules/.guroku/` layout are unchanged from v0.3.
  v1.0 reuses every byte that v0.5 produced.

## 4. What didn't change

To make the scope of v1.0 unambiguous, here is the list of things
that explicitly did **not** change:

- **Resolver semantics.** Still BFS sticky-first, the same algorithm
  shipped in v0.2. PubGrub is still a future direction; no work on
  it landed in v1.0.
- **All CLI subcommands.** `install`, `add`, `remove`, `run`, `exec`,
  `workspaces`, `audit`. No flags were renamed, removed, or
  repurposed.
- **All install and lifecycle behaviour.** Lifecycle scripts run in
  the same order with the same env. `--ignore-scripts` does the same
  thing.
- **The shape of `Manifest`, `Lockfile`, `RegistryClient`,
  `Resolution`, and `Resolved`.** No fields added or removed. No
  signatures changed.
- **`_authToken` and scoped registry behaviour from v0.5.** Same
  wiring, same precedence.
- **`file:` and `git+` dependency behaviour from v0.5.** Same paths,
  same subprocess `git clone`, same cache layout.
- **`overrides` and `resolutions` precedence from v0.5.**

## 5. First-run checklist

1. Build/install v1.0 (`cargo install --path . --locked`, or whichever
   distribution you use). On Windows you can now download the
   prebuilt binary from the release page instead of building.
2. Run your existing project's `guroku install`. No config changes
   required. The lockfile is unchanged; the CAS is unchanged; the
   CLI is unchanged.
3. (Optional) Update any embedder code to use `guroku::prelude::*`.
   The old import paths still work; the prelude is a convenience,
   not a replacement.
4. (Optional) Run `cargo update -p guroku` in any embedder workspace
   to pin to the v1.0 line in its `Cargo.lock`. Embedders that depend
   on guroku via a `^1` constraint will pick up v1.x patch and minor
   releases automatically.

## 6. For library consumers

If you embed guroku as a Rust library, this section is for you. If
you only use the CLI, skip to section 7.

The recommended embedding surface in v1.0 is the prelude:

```rust
use guroku::prelude::*;
```

The prelude re-exports the types you need to drive an end-to-end
install: `Manifest`, `Lockfile`, `RegistryClient`, `Resolution`,
`Resolved`, `GurokuError`, and `Result`. The exact contents are
documented at the top of `src/prelude.rs` and are stable across the
v1.x line.

Direct module imports continue to work. If you have:

```rust
use guroku::manifest::Manifest;
use guroku::lockfile::Lockfile;
use guroku::registry::RegistryClient;
use guroku::error::{GurokuError, Result};
```

you do not need to change anything. The prelude is offered as a
convenience for new code.

The crate-root re-exports are also stable:

```rust
use guroku::{GurokuError, Result};
```

These were already in place in v0.5 and are now SemVer-covered. You
can keep using `guroku::Result` and `guroku::GurokuError` directly.

The one thing to fix in existing code is exhaustive `match`es on
`GurokuError`. Before v1.0 you might have written:

```rust
match err {
    GurokuError::Io(e) => ...,
    GurokuError::Resolution(e) => ...,
    GurokuError::Registry(e) => ...,
    // ... one arm per variant, no wildcard
}
```

Under v1.0 this fails to compile, because `GurokuError` is
`#[non_exhaustive]`. Add a wildcard arm:

```rust
match err {
    GurokuError::Io(e) => ...,
    GurokuError::Resolution(e) => ...,
    GurokuError::Registry(e) => ...,
    _ => return Err(err.into()),
}
```

The wildcard is required even if you currently handle every variant.
The point of the attribute is to let v1.x add new variants without a
breaking release; the wildcard arm is what makes that safe for you.

## 7. For CI/release pipelines

If you publish your own binaries that bundle guroku for Windows, the
v1.0 release artifacts now include `x86_64-pc-windows-msvc` and
`aarch64-pc-windows-msvc`. Switch your downloader to pull those
instead of building from source on a Windows runner. The naming
convention follows the existing Linux and macOS artifacts; see the
release notes attached to the v1.0 tag for the exact filenames.

If you depend on a specific exit code or human-readable error
message in CI (for example, you `grep` install output for a known
phrase), the v1.0 stable behaviour is documented in
`docs/cli-reference.md` and `docs/error-codes.md`. Both files are
considered part of the stable surface for the v1.x line. Anything
not listed there is best-effort.

A typical CI step is unchanged from v0.5:

```yaml
- run: guroku install --frozen-lockfile --ignore-scripts
- run: guroku audit
```

## 8. Reverting

If v1.0 misbehaves on your project, you can downgrade with no data
migration:

1. Install the v0.5 binary.
2. Run `guroku install` as normal.

The lockfile is unchanged, so v0.5 reads it. The CAS is unchanged.
The on-disk `node_modules/.guroku/` layout is unchanged. You do not
need to delete anything.

Library consumers who relied on a `match GurokuError { ... }`
without a wildcard arm will be back in business under v0.5, since
that release does not mark the enum `#[non_exhaustive]`. The
recommended fix is still to add the wildcard arm and stay on v1.0;
the downgrade path is there if you need a bit of breathing room.

## 9. Common errors and fixes

- **`error[E0004]: non-exhaustive patterns` on `match GurokuError`.**
  Add a `_ => ...` arm. See section 6 for the worked example. This is
  the only source-level break in v1.0.
- **`error[E0432]: unresolved import 'guroku::prelude'` (or `cannot
  find module 'prelude' in the crate root`).** Your `Cargo.toml` is
  pinned to a guroku older than v1.0. Bump the version constraint and
  re-run `cargo update -p guroku`.
- **Windows release artifact missing.** If your downloader expects a
  Windows binary at the v1.0 release URL and 404s, double-check the
  target triple in the filename. v1.0 ships
  `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`. The
  `*-gnu` triples are not produced.

If you hit something that isn't covered here, please file an issue
with the output of `guroku --version` and the command you ran.
