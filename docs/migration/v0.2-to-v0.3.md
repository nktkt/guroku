# Migrating from guroku v0.2 to v0.3

This guide covers what changed between guroku v0.2 and v0.3, what you need to
do to upgrade, and how to back out if something goes wrong.

## 1. Why migrate

v0.3 is dramatically faster on warm caches. Two things drive that:

- A content-addressable store (CAS) keyed by SHA-512 of the tarball, so a
  package version is downloaded and extracted at most once per machine
  regardless of how many projects use it.
- ETag-aware metadata caching, so registry GETs for unchanged packages come
  back as `304 Not Modified` and reuse the on-disk JSON.

v0.3 also prevents phantom dependencies via a strict `node_modules` layout:
your project can only `require` packages it actually declared in
`package.json`. Transitive deps live elsewhere and are not visible to your
code.

There are no semantic changes to your `package.json` or `guroku.lock`. The
upgrade is a layout-and-cache change, not a resolver change.

## 2. What changed

- The on-disk store moved. Old layout:

  ```text
  ~/.guroku/store/<name>/<version>/
  ```

  New layout:

  ```text
  ~/.guroku/cas/<sha[0:2]>/<sha[2:]>/
  ```

  Keyed by SHA-512 of the tarball, not by `(name, version)`. Two packages
  that ship byte-identical tarballs share storage; a republished version
  with the same number but different bytes does not collide with the old
  one.

- `node_modules/<name>` is now a symlink, not a directory. It points at:

  ```text
  node_modules/.guroku/<name>@<version>/node_modules/<name>
  ```

  The `node_modules/.guroku/<name>@<version>/node_modules/` directory holds
  the package itself plus symlinks to its direct dependencies, and nothing
  else. That is the strict-layout / phantom-dependency fix.

- Files inside the package directory are hardlinks into the CAS. Extracting
  a tarball happens once; every subsequent project that needs the same
  version links the existing files into place.

- Registry metadata responses are cached at:

  ```text
  ~/.guroku/cache/metadata/<name>.json
  ```

  with an ETag sidecar file next to them. On the next fetch guroku sends
  `If-None-Match`; a `304` response means the cached JSON is reused
  verbatim.

- Library API addition: `RegistryClient::without_http_cache()`. Constructs a
  client that skips the metadata cache entirely. Useful in tests, or when
  you genuinely want to force a network round-trip.

## 3. Behaviour changes that may affect you

### `node_modules/<name>` is a symlink

Tools that hard-coded `node_modules/<name>` as a regular directory -- for
example, walking it without resolving symlinks first -- may behave
differently. The fix on the tooling side is to call `fs::canonicalize` (or
the equivalent in your language) before treating the path as a directory.

In practice almost no real tooling does this; Node itself, bundlers, and
typical scripts all follow the symlink transparently. Flagged here for
completeness.

### Editing files in `node_modules/` mutates the CAS

Because package files are hardlinks into the CAS, modifying
`node_modules/<name>/<file>` modifies the underlying shared bytes. Every
other project on the machine that links the same version sees the edit.

Don't edit packages in `node_modules/` for testing. Use `npm link`, a
workspace, or copy the package somewhere outside the store first.

### Windows symlinks

Creating symlinks on Windows requires either Developer Mode or
administrator privileges. Without one of those, the linker will fail with
`Error creating symbolic link`. See `docs/internals/strict-layout-windows.md`
for the full story and how to enable Developer Mode.

## 4. What didn't change

- The CLI surface. `guroku install`, `guroku add`, `guroku remove`, and
  `--frozen-lockfile` all behave the same way and take the same arguments.
- The lockfile schema. Still `v1`. v0.3 does not rewrite `guroku.lock` on
  upgrade and does not need a migration step for it.
- Resolver semantics. Still BFS with sticky-first behaviour. PubGrub is
  still on the v0.4 roadmap; it is not in this release.
- Public Rust API of:
  - `Manifest`
  - `RegistryClient::fetch_metadata`
  - `RegistryClient::fetch_tarball`
  - `Lockfile::*`

If you import guroku as a library and only use those, your code compiles
unchanged.

## 5. First-run checklist

1. Build or install v0.3:

   ```sh
   cargo install --git https://github.com/nktkt/guroku --tag v0.3.0
   ```

2. Optional: reclaim disk used by the v0.1/v0.2 store layout. Harmless to
   leave, but it will never be read again.

   ```sh
   rm -rf ~/.guroku/store
   ```

3. Optional: in each project, drop the existing `node_modules/` so the next
   install rebuilds with the strict layout instead of leaving the v0.2 flat
   tree in place.

   ```sh
   rm -rf node_modules
   ```

4. Run `guroku install`. The first run populates the CAS and the metadata
   cache.

   ```sh
   guroku install
   ```

5. Run `guroku install` a second time. Notice the speed difference: CAS
   hits skip extraction, ETag `304`s skip metadata downloads.

   ```sh
   guroku install
   ```

## 6. CI

No changes required. `--frozen-lockfile` works the same way and exits with
the same codes. If your CI caches `~/.guroku/`, the cache will pick up
`~/.guroku/cas/` and `~/.guroku/cache/metadata/` automatically; the old
`~/.guroku/store/` path can be dropped from the cache key once nothing on
the runner uses v0.2.

## 7. Reverting

To roll back to v0.2:

1. Install the v0.2 binary (e.g. `cargo install --git ... --tag v0.2.0`).
2. Run `guroku install` in your projects.

The strict-layout `node_modules/.guroku/` directory is ignored by v0.2: it
just rewrites `node_modules/<name>` as a flat directory on the next
install. The new `~/.guroku/cas/` and `~/.guroku/cache/metadata/`
directories are also harmless to leave -- v0.2 does not look at them.

You can also delete them by hand if you want the disk back:

```sh
rm -rf ~/.guroku/cas ~/.guroku/cache
```

## 8. Common errors and fixes

### `Error creating symbolic link` (Windows)

Symlinks are not permitted for your user. Enable Developer Mode in Windows
Settings, or run the shell as administrator. See
`docs/internals/strict-layout-windows.md`.

### `Operation not permitted` on hardlink

Usually means the CAS and the project's `node_modules/` live on different
filesystems, and the kernel refused a cross-device hardlink. The linker
has a copy fallback that should kick in automatically. If you see the
error reach the user instead of being handled, the fallback didn't trigger
-- file an issue with the exact paths involved (CAS root and project
root).

### `lockfile is out of date` after a v0.2 -> v0.3 hop

The lockfile schema is unchanged between v0.2 and v0.3, so a clean upgrade
should never produce this. If it does, it is a bug. File an issue with the
full message, your `package.json`, and your `guroku.lock`.

## 9. Where to file issues

<https://github.com/nktkt/guroku/issues>

v0.3 is the first release with the CAS, the strict layout, and the
ETag-aware metadata cache, so bugs in those areas are the most interesting
ones to hear about. A reproduction that includes your OS, your filesystem
(especially if `node_modules/` and `~/.guroku/` are on different ones), and
the guroku version is the most useful thing you can attach.
