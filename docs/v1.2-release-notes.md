# guroku 1.2.0 — "It backtracks properly"

## TL;DR

v1.2 ships a real PubGrub-based resolver. Diamonds and cascading conflicts that defeated v1.1's single-step backtracking now resolve correctly when a solution exists, and produce structured conflict reports when one doesn't. The v1.0 stability surface (`guroku::prelude`, lockfile, CLI) is unchanged.

## What changed

### `guroku::pubgrub_resolver` (new module)

This is the headline addition. Everything that was painful about v1.1's resolver lives here now, and we've kept the surface narrow on purpose.

- `NpmVersion` — newtype around `node_semver::Version` with `pubgrub::version::Version` impl. The impl is mechanical: `lowest`, `bump`, ordering. The interesting work is on the range side, which we discuss in the scope notes below.
- `resolve_with_pubgrub(client, roots, manifest) -> Result<Resolution>` — the new async entry point. The signature mirrors `guroku::resolver::resolve_with_manifest_overrides` so callers that switch over only need to change the function name.
- Prefetches package metadata BFS-over-names (each package fetched at most once), then hands a synchronous `DependencyProvider` to `pubgrub::solver::resolve`. The split exists because pubgrub itself is synchronous; we do all I/O up front, hold the metadata, and let the solver run on cached data. In practice this is what every npm-style resolver ends up doing.
- File:/git: roots transparently fall back to the v1.1 BFS resolver — no API change for those users. We considered teaching pubgrub about file/git pseudo-versions and decided the complexity wasn't worth it for v1.2.

### `guroku install` (CLI)

The default resolver is now pubgrub. No flag changes; no flag additions. Set `GUROKU_RESOLVER=bfs` to force the v1.1 BFS path. The escape hatch is deliberately an env var rather than a flag — we don't want it to become part of anyone's documented workflow, and env vars are easier to delete in v1.4 once we're confident pubgrub handles every shape we care about.

### `guroku::resolver` (existing module)

v1.1 entry points (`resolve`, `resolve_with_overrides`, `resolve_with_manifest_overrides`) are unchanged. They remain the BFS + single-step-backtracking path. Embedders that prefer that path keep working with no changes. We considered deprecating these and decided against it: the BFS resolver is genuinely faster on the trivial cases that make up most real installs, and we wanted to keep it as a fallback for any pubgrub edge cases we haven't shaken out yet.

### Errors

`GurokuError::ResolutionConflict.requested_by` for pubgrub-produced conflicts now carries pubgrub's human-readable derivation report. The simple-conflict format (`"a > b > c"` from v1.1) is preserved for the BFS path, so anything matching on that string for the BFS resolver continues to work. If you're parsing the field programmatically — please don't, it's a human-readable diagnostic — the variant tag in the underlying enum will tell you which shape you're looking at.

## What didn't change

- `guroku::prelude` — same items, same shapes. No re-exports were added or removed.
- Lockfile schema (`lockfileVersion: 1`) — same. v1.0/v1.1 lockfiles are read by v1.2 unchanged, and lockfiles produced by v1.2 are byte-identical to v1.1 for any input the BFS resolver could solve.
- CLI surface — same subcommands, same flags, same exit codes. `guroku install`, `guroku add`, `guroku remove`, `guroku audit`, `guroku why` all behave identically from the outside.
- Resolved/Resolution shape — adding `aliased_from` was already done in v1.1. No new fields here.

## Migration

Nothing to do. Drop in v1.2; existing projects keep working. If your project hits a pubgrub edge case before we patch it, set `GUROKU_RESOLVER=bfs` to get the old behaviour back, file an issue with your manifest and registry snapshot, and we'll fix it. The BFS path is not going anywhere in the v1.x line.

## Examples

A simple diamond conflict:

```json
{
  "dependencies": {
    "lib-a": "^1",
    "lib-b": "^1"
  }
}
```

where `lib-a@1.2.0` needs `core@^2.5` and `lib-b@1.0.0` needs `core@^2.0 <2.5`. v1.1's single-step backtracker walks `core` once but won't backtrack `lib-a` itself, so it gives up and reports a conflict even though `lib-a@1.1.0` happens to require `core@^2.0` and would have satisfied everyone. v1.2 backs both `lib-a` and `core` to versions that satisfy everyone, and you get a working install with no flag flips.

For the unsatisfiable case — say `lib-a@^2` needs `core@^3` and `lib-b@^1` needs `core@^2` with no overlap — v1.2 prints pubgrub's derivation report instead of v1.1's "first failure wins" line, which makes it dramatically easier to see which constraint is doing the damage.

## Honest scope notes

- Range conversion is "intersection against the prefetched candidate set," not a structural translation. Correct against the candidate set; works for every shape we tested, including the npm tag-version (`latest`, `next`) and url-as-version edge cases. A structural translation would be more elegant and would let us share constraints across registry refreshes; we'll do it in v1.3.
- Path-keyed and glob overrides apply at root classification. Transitive override paths still flow through the v1.1 lookup ladder unchanged. This is a deliberate scope cut for v1.2: we wanted the resolver swap to be the only large change.
- pubgrub 0.2.1 is pinned. v1.3 will track pubgrub 0.3 once it's released.

## What we couldn't ship

- Workspace inter-dep linking. Still v1.3.
- Macrobench harness vs npm/pnpm/bun/yarn. Still future.
- A structural npm-Range to pubgrub-Range translation. v1.3.
