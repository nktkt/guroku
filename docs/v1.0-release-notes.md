# guroku 1.0 — "It's stable"

For nine months guroku has been "the experiment we keep iterating on."
Every minor release reshuffled some piece of the public surface — a
field in the lockfile, an argument to a resolver function, the exact
phrasing of an error message. That was fine while the project was
finding its shape. It is no longer fine. Embedders are starting to ship
guroku as a library inside their own tools; CI pipelines pin specific
CLI invocations; downstream projects are vendoring `guroku-core` and
expecting their imports not to evaporate on the next `cargo update`.

1.0 is the release where guroku stops being an experiment and becomes
a library you can depend on. The headline feature is, quite
deliberately, not a feature: it is a commitment. The lockfile, the
public Rust API, and the CLI surface are now stable under SemVer. We
will not break them in a 1.x. If we ever need to break them, we will
ship a 2.0 — and the bar for that is high enough that it is not on any
roadmap we currently have.

The rest of this document explains exactly what we are committing to,
what is new in the 1.0 cut, what we deliberately left out, and how the
project got here.

## What 1.0 actually means

SemVer is precise but it is also easy to gesture at without saying what
you are pinning. So: here is what guroku 1.0 is pinning, in order of
how often it tends to bite people.

**The lockfile.** `guroku.lock` carries a `lockfileVersion: 1` marker
at the top. As long as that marker reads `1`, the schema is frozen.
Field names will not change. Field types will not change. Nested
shapes will not change. We may add new optional fields in a 1.x — that
is permitted under SemVer because old readers can ignore them — but we
will not remove fields, rename fields, or change the meaning of any
existing field. If we ever need an incompatible schema change, we will
bump to `lockfileVersion: 2`, and the bump itself will be a major
guroku release. The full list of fields and their semantics lives in
`docs/lockfile-format.md`.

**The Rust public API.** Anything reachable through the `guroku::prelude`
module is part of the stable surface. That includes the resolver
entry points, the manifest and lockfile types, the spec parser, the
error enum, and the small number of utility traits embedders actually
need. We will not change a function signature in a 1.x. We will not
remove a public type. We will not narrow a trait bound. New items can
be added; existing ones cannot move. Items outside the prelude — the
internal modules, anything marked `#[doc(hidden)]`, anything not
re-exported — are explicitly not covered by this guarantee, and we
reserve the right to refactor them. If you find yourself reaching past
the prelude, that is a signal to file an issue asking for the missing
piece to be promoted, not a signal to depend on the internal path.

**The CLI surface.** Every documented subcommand, every documented
flag, and every documented exit code is stable. `guroku install`,
`guroku add`, `guroku remove`, `guroku run`, `guroku exec`,
`guroku audit`, `guroku why`, `guroku list`, `guroku cache`, and the
rest will not change their argument shape, their exit codes, or their
fundamental behaviour in 1.x. The exact prose of human-readable output
is *not* covered — error messages can be reworded, progress lines can
be tweaked — but anything a script would `grep` against from
`docs/cli-reference.md` is fixed. If we add a new flag, it will be
purely additive.

The single source of truth for all of the above is `docs/STABILITY.md`,
which spells out the exact boundary in more detail than fits here. If
you are integrating guroku into a long-lived pipeline, read that
document.

## What's new in 1.0

The changes that ship with the major bump are deliberately small. A
1.0 release is mostly about the promise; it is not the place to land
risky features. The list below is everything new.

### Comprehensive rustdoc

Every public item — every type, every function, every trait, every
re-export — now carries a doc comment. The crate root has a top-level
`//!` block that introduces the library to a new reader, sketches the
two or three most common embedding patterns, and links out to the
prelude. Examples in the doc comments are tested as part of CI. There
are no more `// TODO: docs` markers reachable from the prelude.

If you have ever opened `docs.rs/guroku` and bounced because the page
was a wall of bare type names, that experience is gone in 1.0.

### `guroku::prelude`

Embedders previously had to remember the right combination of
`use guroku_core::resolver::Resolver;`, `use guroku_lockfile::Lockfile;`,
`use guroku_manifest::Manifest;`, and so on. The exact spelling
shifted from release to release, which is exactly the kind of churn we
are now committing to stop.

```rust
use guroku::prelude::*;
```

That single line pulls in everything an embedder needs for the
resolve/install/lock workflow. The contents of `prelude` are a
contract: items in there will not be removed in 1.x. If we add new
core types in 1.x, they will be added to the prelude. If we ever need
to remove an item from the prelude, that is a 2.0 change. Full stop.

### `GurokuError` is `#[non_exhaustive]`

The top-level error enum is now marked `#[non_exhaustive]`. This is a
small annotation with a large forward-compat consequence: it forces
downstream `match` arms to include a wildcard, which means we can add
new variants in a 1.x release without breaking any caller. This is the
canonical Rust pattern for "stable enum that may grow," and it is
exactly the situation an error type wants to be in. If you previously
relied on exhaustive matches against `GurokuError`, you will need to
add a `_ =>` arm — that is the one tiny source-level change in 1.0,
and it is called out in the migration guide.

### Pre-built Windows binaries

Previous releases shipped pre-built artifacts for Linux (x86_64,
aarch64) and macOS (x86_64, aarch64). 1.0 adds Windows on both
x86_64 and aarch64. Six platforms total. The release pipeline produces
them on every tagged release. Windows users no longer have to either
build from source or rely on a community Cargo install.

There is one Windows-specific caveat to be aware of: hardlinks behave
differently on NTFS than on the POSIX filesystems we test most heavily.
The store layout still works correctly — that has been validated — but
operations that involve crossing volume boundaries fall back to copying
rather than linking. This is documented in `docs/storage.md`.

### Criterion benchmark scaffolding

There is now a `benches/` directory with criterion harnesses for the
performance-sensitive paths:

- Lockfile parsing — read a lockfile of N entries, measure
  deserialization throughput.
- Manifest parsing — read a `package.json` of N dependencies, measure
  parse + validation throughput.
- Spec classification — given a version specifier string, measure how
  fast we determine whether it is exact, range, tag, file, git, etc.
- Semver matching — given a version and a range, measure how fast we
  decide compatibility.

These are scaffolding, not optimisation work. They exist so that the
next person who wants to make resolution faster has a starting point
and a regression check. Nothing in the 1.0 release is faster than 0.5
because of these — we have not yet done the optimisation pass.
`docs/benchmark-methodology.md` explains how to run them and how to
interpret the results.

## What 1.0 doesn't change

It is worth being explicit about the negatives, because they are the
whole point of a stability release.

The semantics from 0.5 are preserved exactly. The resolver still
behaves the same way given the same inputs. The lockfile written by
0.5 is the lockfile written by 1.0 — same fields, same content
hashes, same ordering. A pipeline that worked under 0.5 works under
1.0 with no edits.

The CLI does not break. Every flag from 0.5 still parses. Every exit
code from 0.5 still has the same meaning. Subcommands keep their
argument order. Help text has been polished but not restructured.

The store layout does not change. `~/.guroku/store/` is byte-compatible
with what 0.5 produced. You do not need to wipe and re-install. Mixing
caches between a 0.5 install and a 1.0 install is fine.

If you take exactly one thing from this release: 1.0 is what 0.5
already was, except now we are willing to sign our name to it.

## By the journey

guroku has been six milestones over its public life. It is worth
saying out loud what each one was about, because the shape of the
project today is the cumulative result.

**v0.1 — the install pipeline.** The first cut was end-to-end install
that worked for a single flat dependency tree. No real resolver, no
real lockfile, no store. A package's tarball got fetched, extracted
into `node_modules/`, and that was the entire story. It established
the CLI shape and the basic expectation that `guroku install` should
behave like the npm command of the same name.

**v0.2 — real resolver and lockfile.** 0.2 replaced the first-cut
"download whatever the manifest says" loop with an actual constraint
solver — the BFS sticky-first solver that still ships today — and
introduced the lockfile as a first-class artifact. Reproducible
installs date from this release. So does the version-specifier parser.

**v0.3 — content-addressed store, hardlinks, strict layout.** 0.3 was
the disk-usage release. Packages stopped being copied per project and
started living in a single shared content-addressed store at
`~/.guroku/store/<integrity>/`. `node_modules` became a tree of
hardlinks into the store, with strict isolation between packages so
that a transitive dependency could not accidentally be `require()`'d
by a package that did not declare it. This is also the release that
introduced the disk-usage and storage docs.

**v0.4 — lifecycle scripts, `run`, `exec`, workspaces.** 0.4 brought
guroku up to feature parity with the daily workflow most JavaScript
developers actually expect. `preinstall`, `install`, and `postinstall`
hooks fire in dependency order. `guroku run <script>` executes
`package.json#scripts` entries with the right `PATH`. `guroku exec` is
the equivalent of `npx`. Workspaces — multi-package repos with a
top-level `package.json` and a `workspaces` field — were brought into
the model, though without the inter-package linking that we still owe.

**v0.5 — private registries, file/git deps, overrides, audit.** 0.5
made guroku usable inside an organisation. `.npmrc` parsing for
authenticated registries. `file:` and `git+https:` dependency sources.
Transitive pinning via `overrides` and `resolutions`. An `audit`
subcommand that talks to the registry advisory database. The release
notes called it "it plays nice."

**v1.0 — stability commitment.** Which brings us to today: no new big
feature, just the promise. That promise is the feature.

## What's not in 1.0 (yet)

We deliberately left several known-wanted things out of the 1.0 cut
because we did not want to ship them rushed. They are all expected to
arrive in a future minor release. None of them require a major bump —
they all fit inside the 1.x compatibility envelope.

**A PubGrub-based resolver.** The current solver is the BFS
sticky-first algorithm that has been in place since 0.2. It is correct
for every input we have tested it against, and it is fast enough for
real workloads, but its error messages on conflict are weaker than what
PubGrub produces. We expect to land a PubGrub backend behind a feature
flag in a 1.x, prove it produces identical resolution outputs on a
corpus, and then promote it to default. The lockfile and the public
API will not change as part of that work.

**Workspace inter-dependency linking.** v0.4 brought workspaces in as
a concept but stopped short of linking workspace packages to each
other inside `node_modules`. A workspace package that depends on
another workspace package today still goes through the registry, which
is wrong. The fix is mechanical but invasive enough that we did not
want to tangle it with the stability release.

**Audit ergonomics.** `guroku audit` exists and is suitable for a CI
gate, but it lacks `--audit-level` (so you can fail the build only on
high or critical findings, not on every advisory), `--json` (so you
can pipe its output to a dashboard), and an `audit fix` subcommand
(so you can mechanically apply the suggested upgrades). All three are
on the post-1.0 list.

**Lifecycle script sandboxing.** Scripts run with the same permissions
as the user invoking guroku. There is no namespacing, no filesystem
restriction, no network policy. This is consistent with how every
other JavaScript package manager behaves, which is exactly why it is
a problem worth eventually fixing. Sandboxing will be opt-in when it
arrives, and it will not break the existing semantics.

We will sequence these in the 1.x stream based on demand, not on the
order in this list.

## Performance note

guroku 1.0 has not been benchmarked head-to-head against the
established package managers in any rigorous sense. We have not run
"install create-react-app fresh ten times and average the wall clock"
against npm, pnpm, yarn, or bun. We have not measured peak resident
memory on a large monorepo. We have not characterised network usage
patterns. None of those numbers exist in any form we would be willing
to publish.

This is deliberate. Performance benchmarking is its own engineering
project — choosing fair workloads, controlling for cache state,
controlling for network, reporting honestly about variance — and we
did not want to ship the 1.0 stability promise alongside numbers we
were not confident in. The criterion suite under `benches/` is the
starting point for that work, not the conclusion of it.

What we *can* say with confidence is that the algorithmic shape of
guroku — content-addressed store, hardlinked `node_modules`, strict
layout — has the same fundamental disk-usage and install-time
characteristics as pnpm, which is the manager guroku most resembles.
Beyond that, please run your own measurements on your own workloads
before drawing conclusions. `docs/benchmark-methodology.md` describes
how to set up a fair comparison.

## What a 2.0 would have to do

A useful way to make a stability promise concrete is to enumerate
exactly what would force us to break it. If any of the following ever
ships, it ships under the version `2.0.0`. None of them are on any
roadmap we currently maintain.

**Bumping `lockfileVersion`.** A new `lockfileVersion: 2` would imply
an incompatible schema change — fields removed, fields renamed,
semantics altered. Old guroku would not read the new lockfile; new
guroku would either need a migration shim or refuse to read the old
one. Either way, the user-visible reality is "your lockfile no longer
works with the version you had pinned," which is exactly what SemVer
exists to signal.

**Renaming a CLI flag.** If `guroku install --frozen-lockfile` were
ever renamed to something else, every CI pipeline pinning that flag
would break in a way no amount of careful release-noting can mitigate.
We would only do this if a flag was so badly named that keeping it was
worse than the breakage, and even then we would prefer to add a new
flag and deprecate the old one in 1.x rather than break in 2.0.

**Removing or restructuring a `prelude` re-export.** If a type
currently re-exported through `guroku::prelude` ever got moved out, or
renamed, or replaced with a structurally incompatible variant, every
embedder's `use guroku::prelude::*;` would start producing different
imports. Trait implementations could appear or disappear silently. The
only safe way to ship that kind of change is the major bump.

To repeat: we have no plans to do any of these. The point of the
list is to be specific about what the 1.x promise covers, not to
foreshadow.

## How to upgrade

If you are coming from 0.5, the migration is essentially a no-op — the
exact set of source-level changes is small enough to fit on one
screen, and the only one most users will hit is the `#[non_exhaustive]`
match-arm change on `GurokuError`. The full step-by-step is in
`docs/migration/v0.5-to-v1.0.md`.

Welcome to a stable guroku.
