# v1.0 Internal Checklist

This document is the contributor-facing answer to the question
"what does v1.0 actually mean?". It is intentionally not a marketing
document. The user-facing release notes live in
`docs/v1.0-release-notes.md`; the migration story lives in
`docs/migration/v0.5-to-v1.0.md`; the long-term compatibility contract
lives in `docs/STABILITY.md`. This file is the audit trail.

## 1. Scope

v1.0 is a stability milestone. It is **not** a feature release.

The shape of the crate, the shape of the lockfile, the shape of the
manifest, the shape of the CLI, and the shape of the on-disk cache are
all what they were at the end of the v0.5 line. The single substantive
change is that we are now committing to those shapes under SemVer:
breaking changes to anything documented as stable now require a 2.0.

In practice this means:

- No new resolver behaviour.
- No new lockfile fields.
- No new CLI subcommands.
- No new manifest keys.
- No new public API items beyond the `prelude` re-export module.

If a v0.5 user runs `cargo install guroku --version 1.0.0`, the only
behaviour they should observe is the version string. Everything else
is intentionally identical.

The point of v1.0 is the SemVer commitment, not the code that
implements it.

## 3. What was deliberately deferred

Each of these has been considered, has either a tracking issue or a
ROADMAP entry, and has been **explicitly excluded** from v1.0. They
are not bugs against 1.0.0. Filing them as such will get the issue
closed with a pointer back to this section.

Resolver and graph:

- PubGrub-based resolver. Target: v1.x.x.
- Workspace inter-dep linking. Target: v1.x.x.

Audit:

- `--audit-level`. Target: v1.x.x.
- `--json` for `audit`. Target: v1.x.x.
- `audit fix`. Target: v1.x.x.

Auth and config:

- npm Basic auth in `.npmrc`. Target: v1.x.x or v2.0, depending on
  whether we can ship it without changing the public credential trait.
- `npm_config_*` environment variable support.
- `${VAR}` interpolation in `.npmrc`.

Lifecycle:

- Sandboxed lifecycle scripts. Target: v1.x.x.

Manifest features:

- Workspace protocol (`workspace:*`).
- Yarn-style `link:./path`.
- npm aliases (`alias@npm:real@^1`).
- Sub-path-aware overrides (`"foo > bar": "1.0.0"`).
- Glob `resolutions` (`**/foo`).

Registry and source backends:

- Tarball downloads from registries that need an `Accept` header
  (notably GitHub Packages).
- Git submodules and sparse checkouts.

Benchmarking:

- Macrobench harness comparing to npm, pnpm, bun, and yarn. The
  Criterion microbenches that did land in v1.0 are deliberately
  scoped to internal hot paths only.

Storage:

- Per-file content-addressed store in the pnpm v3 style.

For each of the above, the v0.5 behaviour (i.e. either "not
supported" or "best-effort fallback") is preserved exactly. None of
these were partially implemented and then disabled; they were never
implemented in this line at all.

## 4. What was deliberately re-implemented but not in v1.0

None. Everything from v0.5 is preserved unchanged.

This section exists explicitly so that a future maintainer auditing
the v1.0 to v2.0 jump can confirm there is no hidden carry-over of
"we silently rewrote X under the hood". There is no such X.

If you find one, that is a bug, not a deliberate omission from this
list.

## 7. Sign-off criteria

These are the gates that had to be green before tagging `v1.0.0`.
They are reproduced here so that the same gates can be re-run by any
contributor on a clone of the tag.

- All test files pass on Linux and macOS.
  Windows is in CI but is not a release blocker for the initial
  `1.0.0` tag; it becomes a blocker from `1.0.1` onwards.
- `clippy --all-targets --D warnings` is clean.
- `cargo fmt --check` is clean.
- `cargo doc --no-deps --all-features` is clean with `-D warnings`.
  This is what catches broken intra-doc links in the prelude
  re-exports and in the freshly written crate-level rustdoc.
- The stability tests under `tests/api_stability_*.rs` compile.
  They are designed so that compilation itself is the assertion: if
  a public item changes name, signature, or visibility, these files
  fail to build.
- The lockfile-format stability tests pass against the v1 fixtures.
  Specifically, `tests/lockfile_v1_compat.rs`,
  `tests/lockfile_unknown_field.rs`, and
  `tests/lockfile_format_stability.rs` must all pass against the
  fixtures committed under `tests/fixtures/lockfile/v1/`.
- The `CHANGELOG` entry for `1.0.0` is finalised, has a real date
  (not "Unreleased"), and references the migration guide.

If any of the above are not green, the release is not v1.0. It is
either a release-candidate or a v0.5 patch. There is no
"good enough" path for the SemVer commitment; the entire point of
the milestone is that the commitment is unconditional.
