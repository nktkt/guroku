# v1.1 Internal Checklist

This document is the contributor-facing answer to the question
"what does v1.1 actually mean?". It is intentionally not a marketing
document. The user-facing release notes live in
`docs/v1.1-release-notes.md`; the migration story lives in
`docs/migration/v1.0-to-v1.1.md`; the long-term compatibility contract
continues to live in `docs/STABILITY.md`. This file is the audit
trail, and it mirrors the format established in
`docs/internals/v1.0-checklist.md`.

## 1. Scope

v1.1 is the first feature minor after the v1.0 stability commitment.
Where v1.0 was about freezing the shape of the crate and signing the
SemVer contract, v1.1 is about adding the first round of
already-deferred user-visible features without breaking that contract.

The release adds three user-visible features and one resolver
improvement:

- npm-style aliases in the manifest (`alias@npm:real@^1`).
- Path-keyed overrides (`"foo > bar": "1.0.0"`), where the key
  encodes a position in the dependency graph rather than just a
  package name.
- Glob-style `resolutions` (`**/foo`), restricted to the
  double-star-then-name shape; richer glob shapes are explicitly
  out of scope and are listed in section 3.
- Single-step backtracking in the resolver, so that a single failed
  candidate no longer aborts the entire resolution.

Everything that v1.0 promised remains promised. The crate root,
`prelude`, lockfile shape, manifest shape (modulo additive keys
gated behind the new features), CLI shape, and on-disk cache shape
are all backwards compatible with v1.0.0. Any v1.0 user upgrading
to 1.1.0 should observe no behaviour change unless they opt into
one of the new features in their `package.json`.

## 2. What landed in v1.1

Crate metadata and surface:

- Crate version bumped to `1.1.0` in `Cargo.toml`.
- `DepSpec::Alias { real_name, inner }` variant added, plus
  `#[non_exhaustive]` on `DepSpec` itself so that future spec kinds
  can be added in v1.x without a SemVer break.
- `overrides::lookup_with_path` for path-aware override resolution,
  plus `classify_entries` and the supporting types
  `OverrideEntry`, `OverrideKind`, and `OverrideSource`.
- `resolver::resolve_with_manifest_overrides` as the new public
  entry point that ties manifest-level overrides and resolutions
  into the resolver in one call.
- `Resolved::aliased_from` accessor so that consumers can recover
  the original alias name from a resolved package.
- `ChosenEntry::metadata_name` and `ChosenEntry::original_range`
  threaded through the resolver. These remain private; they are
  documented in `docs/internals/single-step-backtrack.md` because
  the backtracking logic depends on them, not because they are part
  of the public surface.
- Single-step backtracking is implemented via the internal
  `try_backtrack` helper. The helper is private; the behavioural
  guarantee (one level only, never re-walks transitive deps) is
  what is public.
- `ResolutionConflict.requested_by` now carries a path through the
  dependency graph, not just an immediate parent. This is an
  additive change to an already-public error variant.
- `cas_paths` is now keyed by *local* dependency name (i.e. the
  name as it appears in `package.json`, post-alias) in both
  `install_from_resolution` and `into_linked_packages`. This is
  the install-side counterpart to alias support.

Tests (new files in `tests/`):

- `tests/specs_alias_*.rs` — parser and round-trip tests for
  `npm:`-prefixed dep specs.
- `tests/overrides_*.rs` — path-keyed override matching, including
  ordering and shadowing rules.
- `tests/manifest_alias_round_trip.rs` — confirms aliased entries
  survive a parse-then-serialise round trip with the original key.
- `tests/error_resolution_path.rs` — pins the new path-bearing
  shape of `ResolutionConflict.requested_by`.
- `tests/resolver_*.rs` — backtracking behaviour, including the
  no-multi-level guarantee.
- `tests/cli_help_v1_1_no_new_subcommands.rs` — explicit assertion
  that v1.1 does not add CLI subcommands. The new features are
  surfaced via the manifest, not via CLI.

## 3. What was DELIBERATELY deferred

Each of these has been considered, has either a tracking issue or
a ROADMAP entry, and has been **explicitly excluded** from v1.1.
They are not bugs against 1.1.0. Filing them as such will get the
issue closed with a pointer back to this section.

Resolver:

- Full PubGrub-based resolver. Target: v1.2. The single-step
  backtracking that landed in v1.1 is intentionally a stopgap; it
  fixes the most common "one bad candidate fails the whole tree"
  case without committing us to PubGrub's data model.
- Multi-level backtracking. Excluded from v1.1 because it would
  require re-walking transitive deps, which in turn would force a
  rethink of how `cas_paths` is populated. Folded into the v1.2
  PubGrub work.

Aliases:

- Aliases in `peerDependencies` and `optionalDependencies`. Only
  `dependencies` and `devDependencies` are supported in v1.1.
- Aliases targeting non-registry sources (e.g.
  `npm:foo@file:./pkg`, `npm:foo@git+https://...`). The grammar
  reserves the syntactic space; the resolver rejects it.
- Auto-cleanup of orphaned aliases on `guroku remove`. The remove
  path in v1.1 leaves alias entries in `node_modules` exactly as
  v1.0 did; cleaning them up requires a graph-walk that is folded
  into the v1.2 resolver work.

Path-keyed overrides:

- Wildcards in path keys (`"a > * > b"`). Only literal package
  names separated by `>` are supported in v1.1.

Glob resolutions:

- Richer glob patterns: `pkg/**/foo`, `*-helper`, brace expansion
  (`{a,b}`), and any other shape beyond the documented
  double-star-then-name form.
- Negation patterns (`!pkg`).
- OR patterns / multiple alternatives in a single key.

For each of the above, the v1.0 behaviour (either "not supported"
or "rejected at parse time") is preserved exactly. None of these
were partially implemented and then disabled; they were never
implemented in this line at all. The deferred-features section of
the ROADMAP is the source of truth for which release is going to
pick each of these up.

## 4. Sign-off criteria for tagging v1.1.0

These are the gates that had to be green before tagging `v1.1.0`.
They are reproduced here so that the same gates can be re-run by
any contributor on a clone of the tag.

- All test files pass on Linux and macOS. macOS is a release
  blocker from 1.1.0 onwards (it was not for the initial 1.0.0
  tag, but became one from 1.0.1; v1.1 inherits that gate).
- `clippy --all-targets -- -D warnings` is clean.
- `cargo fmt --check` is clean.
- `cargo doc --no-deps --all-features` is clean. The new
  internals docs and the user-facing feature docs both exercise
  rustdoc's intra-doc link resolution against the additions to
  `DepSpec`, `overrides`, and `resolver`, so a broken link in any
  of those modules surfaces here.
- `cargo-semver-checks` confirms no breaking changes to the
  prelude API surface. The additions to non-prelude types
  (`DepSpec::Alias`, `OverrideEntry`, `OverrideKind`,
  `OverrideSource`, the new `resolver` entry point, and the
  additive change to `ResolutionConflict.requested_by`) are
  non-breaking by construction: every new variant lives behind a
  `#[non_exhaustive]` enum, and every new field is on a struct
  that was already `#[non_exhaustive]` in v1.0.
- The `CHANGELOG` entry for `1.1.0` is finalised, has a real
  date (not "Unreleased"), and references the migration guide.
- The `README` is updated to mark v1.1 as shipped, with the
  install instructions still pointing at the v1.x line in
  general rather than at a specific patch version.

If any of the above are not green, the release is not v1.1. It is
either a release-candidate or a v1.0 patch. There is no
"good enough" path for a feature minor on top of a stability
commitment; the contract from v1.0 is what makes the additions in
v1.1 safe to ship at all.
