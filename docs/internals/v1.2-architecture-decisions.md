# v1.2 Architecture Decisions

This document captures the architectural decisions made during the v1.2
release cycle, in ADR (Architecture Decision Record) form. Each entry
records the context, the decision, the consequences, and the
alternatives that were considered and rejected.

---

# ADR-1: Use pubgrub-the-crate 0.2 instead of writing our own solver

Status: Accepted

Context: The v1.1 BFS sticky-first resolver works for the common case
but hits cascading conflicts as soon as the dependency graph contains
non-trivial diamond shapes. We saw this most often in projects that pin
a transitive twice through different intermediaries; the BFS resolver
either picks an early candidate that later proves infeasible, or it
explores a frontier so large that solve times degrade super-linearly.
Writing a proper unit-propagation solver in-house was estimated at one
engineer-quarter and would carry an indefinite maintenance tail.

Decision: Pin `pubgrub = "0.2"` and use it as the default resolver in
v1.2.

Consequences: We take on an external dependency in a critical path and
inherit its semver discipline. On the other hand we have one fewer
algorithm to maintain, and pubgrub's conflict explanations are
strictly better than what BFS produces. We pay for 0.2's API surface;
bumping to 0.3 (which restructures `DependencyProvider`) is deferred
to v1.3.

Alternatives considered: an in-house pubgrub-style implementation (too
expensive, no obvious correctness story); extending the BFS resolver
with full backtracking (still quadratic in the worst case, and
duplicates work pubgrub already does well).

# ADR-2: Keep the v1.1 BFS resolver as `GUROKU_RESOLVER=bfs` opt-out

Status: Accepted

Context: Pubgrub bugs are real, and even a correct solver can pick
versions that surprise users who have built habits around the BFS
ordering. We need an escape hatch so a regression in the new resolver
does not block a release.

Decision: Both resolvers ship in the binary. The default is pubgrub;
setting `GUROKU_RESOLVER=bfs` selects the v1.1 resolver.

Consequences: The binary carries two resolver implementations, which
adds compile time and a small amount of runtime weight. In return we
get operational simplicity for users who hit edge cases: the workaround
is one environment variable, not a downgrade. We commit to maintaining
BFS for at least the v1.x line.

Alternatives considered: ship only pubgrub and tell affected users to
pin the previous guroku version (rejected: too disruptive); drop BFS
entirely after a deprecation cycle (deferred to v1.3 at the earliest).

# ADR-3: Two-phase async-prefetch + sync-solve

Status: Accepted

Context: Pubgrub's `DependencyProvider` trait is synchronous, but our
registry client is async and concurrent by design. Calling `block_on`
inside the trait would either deadlock the runtime or force a separate
runtime per solve.

Decision: Run the resolver in two phases. Phase one walks the project
roots with the existing async fetcher and eagerly prefetches every
reachable package name into the in-memory cache. Phase two hands that
populated cache to pubgrub, which then runs entirely synchronously
against it.

Consequences: Cold runs do more network than strictly necessary,
because we fetch reachable packages whose versions pubgrub may never
inspect. In exchange the solver phase is deterministic, easy to
profile, and free of any async/sync impedance. Behaviour is
predictable: the network is done before solving begins.

Alternatives considered: `block_on` inside `DependencyProvider`
(rejected: runtime hazards); lazy fetch with thread-bouncing between a
sync solver thread and an async I/O thread (rejected: complexity for
marginal network savings).

# ADR-4: Candidate-set range translation, not structural

Status: Accepted

Context: npm semver `Range` types are a union of comparator sets with
their own normalisation rules; pubgrub `Range` types are interval
unions over a `Version` trait. A structural translation has to handle
every comparator shape and prove the translation preserves semantics.

Decision: After prefetch, build the pubgrub `Range` for a requirement
as the union of singletons over the prefetched candidates that satisfy
the npm range. We never translate ranges structurally.

Consequences: The translation is correct against the candidate set by
construction, simple to implement, and easy to test (the test is just
"for each candidate, does the npm matcher agree with the pubgrub
matcher?"). Performance is bounded by the size of the candidate set,
which for normal registries is small.

Alternatives considered: structural translation per comparator
(rejected: large surface area, hard to keep correct as npm-semver
evolves).

# ADR-5: Synthetic root package `$guroku-root`

Status: Accepted

Context: Pubgrub solves rooted at a single `(package, version)` pair.
A guroku project may declare multiple top-level dependencies plus dev
and optional roots, none of which is a single package.

Decision: Invent a synthetic root package named `$guroku-root` with
version `0.0.0`. Its dependency map is the union of the project's
roots, and it is the package handed to pubgrub as the entry point.

Consequences: Multiple project roots are supported trivially, and the
solver treats them uniformly. The `$` prefix is unparseable as a real
npm package name, so collision with a real registry package is
impossible.

Alternatives considered: solve each root in a separate pubgrub run and
merge results (rejected: cross-root conflicts would not be detected
inside pubgrub; we would have to reimplement unification on top).

# ADR-6: Aliases decomposed at root classification, not inside pubgrub

Status: Accepted

Context: Pubgrub does not model "this package's local name in my
project differs from its name in the registry." npm aliases of the
form `npm:<real>@<spec>` are exactly that, and we need them to keep
working.

Decision: At `plan_roots` time, decompose every `npm:<real>@<spec>`
into a `(real_name, spec)` pair for pubgrub's solve, and remember the
local-name to real-name mapping in a side table. The materialise step
later rebuilds the local-name keying when writing `node_modules`.

Consequences: Pubgrub never sees aliases; it solves over real registry
names only. Alias handling is concentrated at two points (root
classification and materialise) rather than smeared through the
solver.

Alternatives considered: extend pubgrub's `Package` type to carry alias
information (rejected: would force a fork or a complex newtype, and
would couple alias semantics to the solver).

# ADR-7: file:/git: roots fall back to the v1.1 BFS resolver

Status: Accepted

Context: Pubgrub's model is candidate-version selection from registry
metadata. `file:` and `git:` dependencies do not have versions in the
sense pubgrub expects, and synthesising versions for them would
introduce a parallel namespace that pubgrub's conflict explanations
cannot describe usefully.

Decision: When any root is `file:` or `git:`, the pubgrub entry point
delegates the entire solve to the v1.1 BFS resolver.

Consequences: Mixed projects (some registry deps, some local or git
deps) use BFS even though most of the graph is registry-shaped. This
is acceptable for v1.2: the affected projects are exactly the ones
where BFS already worked. v1.3 may unify the two paths by modelling
file/git deps as single-version packages in the cache.

Alternatives considered: model `file:`/`git:` as a single-version
package in the candidate cache (rejected for v1.2 on schedule grounds;
revisit in v1.3).

# ADR-8: Don't surface structured fields in pubgrub-produced ResolutionConflict

Status: Accepted

Context: A pubgrub conflict spans multiple packages and multiple
incompatibilities, and its natural representation is a derivation
tree. The v1.1 `ResolutionConflict` type was designed around BFS,
where a conflict has a clear "this package wanted that version"
shape, and exposes `name`, `chosen`, and `requested` as structured
fields.

Decision: For pubgrub-produced conflicts, fill the structured fields
with placeholders (the literal string `<resolver>` for `name`,
`chosen`, and `requested`) and put pubgrub's `DefaultStringReporter`
output into `requested_by` as a multi-line narrative.

Consequences: Tests that asserted on structured fields keep working
for BFS conflicts. Pubgrub conflicts are recognisable at a glance by
their `<resolver>` placeholder. End users get a readable narrative in
the place where they were already looking.

Alternatives considered: parse pubgrub's derivation tree to extract
synthetic structured fields (rejected: brittle, and the extracted
fields would lie about the shape of the conflict); require users to
read the derivation tree directly (rejected: regression in UX).

# ADR-9: Lockfile schema unchanged

Status: Accepted

Context: v1.0 froze the lockfile schema as a stability commitment.
v1.2 changes the resolver but not the set of facts a lockfile needs to
record.

Decision: Honour the v1.0 freeze. v1.2 produces lockfiles that are
bit-compatible with v1.0/v1.1 readers.

Consequences: Users can downgrade from v1.2 to v1.0 or v1.1 without
losing or rewriting their lockfile, which makes adoption low-risk. We
forgo the chance to record pubgrub-specific metadata (such as the
derivation tree) in the lockfile.

Alternatives considered: bump to `lockfileVersion: 2` with
pubgrub-specific metadata (rejected: breaks the v1.0 stability
commitment for no concrete user benefit).

# ADR-10: GUROKU_RESOLVER as env var, not CLI flag

Status: Accepted

Context: v1.0 froze the CLI surface as a stability commitment.
Resolver selection is an operational knob, not a workflow command.

Decision: Resolver selection is exposed via the `GUROKU_RESOLVER`
environment variable. The CLI is unchanged.

Consequences: The env var is discoverable through documentation but
not through `guroku --help`. This is acceptable: the default is the
right choice for the overwhelming majority of users, and the people
who need the escape hatch are exactly the people who will read the
release notes.

Alternatives considered: a `--resolver` flag (rejected: would break
the v1.0 CLI freeze); a user-config option in `.guroku.toml`
(rejected: adds a new config surface for a knob we expect to retire
once pubgrub stabilises).
