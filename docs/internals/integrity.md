# Package Integrity Verification

This document describes how guroku verifies the integrity of npm package
tarballs in v0.1. It is aimed at contributors who want to understand or
extend the verification path.

## Threat model

Guroku v0.1 defends against:

- **Tampered tarballs in transit.** A network attacker (e.g. a hostile
  proxy, a misconfigured caching layer, an attacker on an untrusted Wi-Fi)
  swapping or modifying the tarball bytes between the registry and our
  client.
- **Registry mirror corruption.** A mirror or CDN edge node that returns
  a corrupted or stale tarball — whether from disk rot, a buggy
  deployment, or a partial cache poisoning attempt.
- **Byte-flips.** Single-bit corruption from flaky disks, flaky NICs,
  or anything else that mutates bytes between the upstream registry's
  metadata and what we actually receive.

What guroku v0.1 does **not** defend against:

- **A fully malicious npm registry that lies about both the
  `dist.integrity` field and the tarball.** If the same actor controls
  both the metadata and the bytes, the integrity field is just whatever
  hash they want it to be, and we will happily verify it. Defending
  against this requires out-of-band package signing (e.g. Sigstore-style
  attestations published independently of the registry). Signing is
  planned for a future milestone and is explicitly out of scope for v0.1.

## The npm `integrity` field

npm registries return an `integrity` string in the `dist` block of every
version document, for example:

```
"dist": {
  "tarball": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
  "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvSg==",
  "shasum": "679591c564c3bffaae8454cf0b3df370c3d6911c"
}
```

The format is:

```
<algo>-<base64(digest)>
```

This is the [Subresource Integrity ("SRI")](https://www.w3.org/TR/SRI/)
format, which the W3C originally specified for `<script integrity="...">`
on the web platform and which npm reused for package metadata. The
algorithm token is one of `sha256`, `sha384`, `sha512`. The digest is
the raw bytes of the hash, base64-encoded (standard base64, with `=`
padding).

The SRI spec also allows a space-separated list of alternatives, e.g.
`sha384-AAA== sha512-BBB==`. Guroku v0.1 does not implement that; see
"Future work" below.

## What guroku v0.1 supports

Only `sha512`.

The following all return an `UnsupportedIntegrity` error today:

- `sha1-...` integrity strings
- `sha256-...` integrity strings
- The legacy `dist.shasum` field (a bare hex SHA-1)
- Any unknown algorithm token

In practice this is rarely a problem: SHA-512 has been the npm
registry's universal default for the `integrity` field since 2017.
Packages published before then typically still have a SHA-512
`integrity` regenerated by the registry, even though the original
`shasum` is preserved alongside it.

## Verification flow

```
download tarball bytes
let (algo, b64) = integrity.split_once('-')
if algo != "sha512": Err(UnsupportedIntegrity)
let expected = base64::decode(b64)
let actual = SHA-512(bytes)
if actual != expected: Err(IntegrityMismatch)
```

`UnsupportedIntegrity` and `IntegrityMismatch` are distinct error
variants on purpose. The first is a configuration / compatibility
problem (we cannot verify, even in principle); the second is a security
signal (we tried to verify, and the bytes did not match).

## Where verification happens

Verification lives in `commands::install_version`, and runs **before**
the tarball is extracted. The flow is:

1. Resolve the version, obtaining `tarball_url` and `integrity`.
2. Download the tarball into an in-memory buffer.
3. Run the verification flow above on that buffer.
4. Only on success, hand the buffer to the extractor.

We never write unverified bytes to disk. In particular, we do not stream
the tarball straight into the extractor and check the hash on the way
through — the entire byte stream is hashed and compared against the
expected digest before any extraction begins. This keeps the failure
mode simple: if integrity verification fails, nothing changes on disk,
and there is no half-extracted package to clean up.

## Constant-time comparison

We currently compare the actual and expected digests with a plain `==`
on byte slices. This is **not** constant-time.

For our use case this is fine. Constant-time comparison matters when an
attacker can submit many guesses against an authentication MAC and
learn timing-side-channel information about which prefix is correct.
Here, the "secret" is a public hash of public bytes, and the attacker
gets one shot per tarball: either the bytes hash to the expected value
or they don't. Timing leaks nothing useful.

We mention it for completeness, and we may revisit if guroku ever
checks an authentication MAC (for example, a per-user signed manifest)
where constant-time comparison would actually matter.

## What's missing in v0.1

- **No `dist.shasum` fallback.** Very old packages that publish only
  the legacy SHA-1 `shasum` and no `integrity` will fail with
  `UnsupportedIntegrity`. We would rather refuse to install than
  silently rely on SHA-1.
- **No signature verification.** As covered in the threat model, we
  trust the registry's `integrity` field. A registry that lies about
  both the integrity and the bytes is not detected.
- **No store-side rehash on read.** Once a tarball has passed
  verification and has been extracted into the on-disk store, we do
  not re-hash the extracted form when later commands read from it. We
  trust the local filesystem.

## Future work

- **Signed packages.** Sigstore-style attestations, verified against a
  transparency log, would let us detect a malicious or compromised
  registry. This is the main planned upgrade to the threat model.
- **Rehash on store read.** Periodically, or on every read, re-hash
  the extracted tree against a digest captured at install time. This
  catches local corruption and tampering of the on-disk store.
- **Multiple algorithms in a single integrity string.** The SRI spec
  allows a space-separated list of `<algo>-<digest>` alternatives, and
  recommends that the verifier pick the strongest algorithm it
  understands. Implementing this would let guroku gracefully accept
  packages that publish, e.g., both `sha384` and `sha512`, and would
  give us a clean migration path the next time the ecosystem rotates
  hash algorithms.
