# guroku 0.2 — "It resolves correctly"

The 0.1 release of guroku was a proof of concept: it could fetch a tarball from a
registry, unpack it into `node_modules`, and call that an install. It worked, in
the narrow sense that simple cases produced files on disk. It did not, however,
resolve dependencies correctly. Any version range more interesting than an exact
match got coerced to whatever happened to be tagged `latest`, and there was no
lockfile to record what had actually been chosen. That was fine for a demo, but
it was not a package manager.

The 0.2 milestone exists to close that gap. The headline is in the title: as of
this release, guroku resolves semver ranges the way npm does, writes the result
to a real lockfile, and reads that lockfile back deterministically. The install
pipeline downstream of resolution is mostly unchanged — that is the next
milestone's job — but the part that decides *which versions go on disk* is now
a real implementation rather than a placeholder. If you tried 0.1 and bounced
off because the resolver was a toy, this is the release where guroku starts
behaving like something you could plausibly use.

## What's new

### Real semver

The resolver now understands the full set of npm-style range operators. Concrete
examples of what works:

- **Caret ranges** — `^1.2.3` matches `>=1.2.3, <2.0.0`. For `0.x` versions,
  caret is tightened the way npm tightens it: `^0.2.3` matches `>=0.2.3, <0.3.0`,
  and `^0.0.3` matches only `0.0.3`.
- **Tilde ranges** — `~1.2.3` matches `>=1.2.3, <1.3.0`. `~1.2` matches
  `>=1.2.0, <1.3.0`. `~1` matches `>=1.0.0, <2.0.0`.
- **Hyphen ranges** — `1.2.3 - 2.3.4` matches `>=1.2.3, <=2.3.4`. Partial
  versions on either side expand the way the spec says they should.
- **X-ranges** — `1.2.x`, `1.x`, and `*` all do what you would expect. A bare
  `*` (or empty string, or `latest`) matches any published version.
- **OR composition** — `^1.2.3 || ^2.0.0` resolves against the union of the two
  ranges, picking the highest matching version across both.
- **Comparator chains** — `>=1.2.3 <2.0.0` is now a first-class range, not a
  parse error.

Prereleases follow the npm rule: a range like `^1.2.3` will not match `2.0.0-beta.1`
unless the range itself names a prerelease, in which case prereleases on that
exact `MAJOR.MINOR.PATCH` are eligible.

If a manifest specifies a range that no published version of the package
satisfies, the resolver fails loudly. See **Breaking changes** below.

### A real lockfile

guroku now writes `guroku.lock` at the root of your project. The format is
documented in `docs/lockfile-format.md`; the short version is that it records,
for every package in your dependency graph:

- the resolved version,
- the resolved tarball URL,
- the integrity hash (SHA-512, base64, prefixed with `sha512-`),
- and the set of dependencies it was resolved against.

The lockfile is the source of truth for reproducible installs. Commit it. If
you have ever debugged a "works on my machine" install where two developers got
different transitive versions out of the same `package.json`, the lockfile is
the fix for that class of bug.

When `guroku install` runs and a lockfile is present, the resolver will reuse
the locked version for any (package, range) pair already pinned, and only
re-resolve entries that are new or whose range has changed. Adding a new
dependency does not perturb existing ones.

### `--frozen-lockfile` for CI

Pass `--frozen-lockfile` to `guroku install` and the resolver becomes read-only:
if the lockfile is missing, out of date relative to `package.json`, or would
need to change for any reason, the install fails. This is the flag you want in
continuous integration.

### peerDependencies and optionalDependencies in the manifest

The manifest parser now recognizes `peerDependencies`, `peerDependenciesMeta`,
and `optionalDependencies`. They are read in, preserved through any
serialization round-trip, and surfaced to the resolver. Note the limitation:
**guroku does not yet act on them at install time**. peerDependencies are not
checked against the installed graph, and optionalDependencies are not
optionally installed — they are currently treated like ordinary dependencies if
you list them, or ignored if you put them in `optionalDependencies` only. Full
semantics are scheduled for a later release. The manifest fields exist now so
that registries and tooling that emit them do not cause guroku to choke or
silently drop data.

See `docs/peer-dependencies.md` and `docs/optional-dependencies.md` for the
current state and the intended future behavior.

## Breaking changes

- **Unsatisfiable ranges are now errors.** In 0.1, a range like `^99.0.0` against
  a package whose highest published version was `1.4.2` would silently fall
  back to installing `latest`. This was wrong, it hid bugs, and it has been
  removed. The resolver now returns an error naming the package and the range,
  and the install aborts. If you were relying on the fallback (you should not
  have been), pin to an explicit range that actually has candidates.
- **Library API rename.** `RegistryClient::default` has been renamed to
  `RegistryClient::with_default_registry`. The old name collided with the
  `Default` trait in a way that made the call site ambiguous depending on
  context, and the new name is what the function actually does. This only
  affects callers using guroku as a library; the CLI is unaffected.

## What didn't change

A short list of things that are deliberately the same as 0.1, so you know not
to look for them:

- **The install pipeline.** Tarballs are still fetched, verified against their
  integrity hash, and unpacked. The fetch and unpack code is unchanged.
- **The `node_modules` layout.** Still flat, still copy-based. Every package in
  the dependency graph is copied into `node_modules/<name>/`. There is no
  hoisting yet beyond the natural flattening that comes from picking one
  version per package name. There is no content-addressable store and no
  hardlinking. That work is queued for 0.3 — see below.
- **The CLI surface.** The only addition is the `--frozen-lockfile` flag on
  `guroku install`. No commands were renamed, no flags were removed, no output
  formats changed. If you have scripts that wrap the 0.1 CLI, they should
  continue to work.

## What's coming in v0.3

The next milestone is about disk and link layout, not resolution. The headline
features:

- **Content-addressable store at `~/.guroku/store`.** Every tarball gets
  unpacked once, into a path keyed by its integrity hash. Subsequent installs
  of the same `(name, version, integrity)` tuple — across every project on the
  machine — reuse the unpacked copy. No more re-extracting `lodash` for the
  hundredth time.
- **Hardlink-based linking.** Project `node_modules` entries become hardlinks
  into the store rather than full copies. Disk usage drops to roughly the size
  of the store plus one inode per linked file per project. Installs get faster
  because the per-file work is `link(2)`, not `read+write`.
- **pnpm-style strict `node_modules` layout.** Each package only sees the
  dependencies it actually declared. No more accidentally importing a
  transitive dependency that happens to be hoisted next to you. This is a
  correctness change as much as a layout change.

The full roadmap, including what comes after 0.3, lives in the README. This
section is the short version.

## How to upgrade

A step-by-step migration guide, including how to generate your first
`guroku.lock` and what to do about the `RegistryClient::default` rename, lives
at [`docs/migration/v0.1-to-v0.2.md`](migration/v0.1-to-v0.2.md). For most
users the upgrade is: bump the binary, run `guroku install` once to write a
lockfile, commit the lockfile, add `--frozen-lockfile` to your CI install
command. That's it.
