# guroku 0.5 — "It plays nice"

The 0.4 series got guroku self-sufficient: a content-addressed store, a
strict `node_modules`, deterministic lockfiles, lifecycle scripts, and the
CLI surface most users actually reach for. What it could not do was live
inside a real engineering org. If your packages came from `acme.internal`
instead of `registry.npmjs.org`, if half your `package.json` pointed at
`git+https://...` forks, or if security review insisted on an `audit`
gate in CI, guroku had nothing to say. 0.5 is the release that makes
guroku show up to work: private registries with token auth, `file:` and
`git+https:` dependency sources, transitive version pinning via
`overrides` and `resolutions`, and an `audit` subcommand that talks to
the registry's advisory database. It plays nice with the world that
already exists.

## What's new

### Private-registry support

`.npmrc` parsing graduated from "we read the default registry URL" to a
full credential-and-routing layer.

- `_authToken` (and per-registry `//host/path/:_authToken=...`) is
  attached as `Authorization: Bearer <token>` on every outgoing HTTP
  request, including tarball downloads.
- Scoped registry directives — `@acme:registry=https://acme.internal/npm/` —
  actually route. A request for `@acme/widget` goes to the scoped
  registry; everything else goes to the default. Tokens are matched by
  registry host, so a request to the public registry will not leak your
  internal token.
- `always-auth=true` is honored for registries that require auth on
  tarball fetches as well as metadata.

See `docs/private-registries.md` for the full configuration matrix.

### `file:` dependencies

`"my-lib": "file:../my-lib"` now resolves to the local path, hardlinks
the source tree into the store, and links it into `node_modules` like
any other package. The lockfile records the resolved absolute path so a
fresh `guroku install` on the same machine is reproducible; the
`integrity` field is computed over the hardlinked content.

Caveats and exact semantics live in `docs/file-deps.md`.

### Git dependencies

Three forms are supported:

- `git+https://github.com/user/repo.git`
- `git+https://github.com/user/repo.git#<ref>` where `<ref>` is a tag,
  branch, or commit SHA.
- `github:user/repo` and `github:user/repo#<ref>` shorthand.

Clones happen via a subprocess `git` call (we do not bundle a git
implementation) into `~/.guroku/cache/git/<host>/<owner>/<repo>/<ref>/`.
Subsequent installs reuse the cache. The resolved commit SHA is pinned
in the lockfile so a moving `#main` ref is captured at install time and
locked thereafter.

See `docs/git-deps.md`.

### `overrides` and `resolutions`

`package.json#overrides` (npm 8+ syntax) and `resolutions` (yarn
syntax) both pin transitive versions during resolution. If both are
present, `overrides` wins; a warning is emitted. Only the
flat-key form is matched in 0.5 — see "Known limitations" below.

### `guroku audit`

A new subcommand that POSTs the lockfile's package set to the
configured registry's advisory endpoint (`/-/npm/v1/security/advisories/bulk`
on npm-compatible registries) and prints findings grouped by severity.
Exit code is non-zero if any advisory is returned, which makes it
suitable for a CI gate. Output is human-readable text in 0.5; structured
output is on the v0.6 list.

## What this means in practice

- **Big-corp npm at `acme.internal`.** Drop a `.npmrc` with the
  registry URL and an `_authToken` into the project (or `~/.npmrc`),
  and `guroku install` Just Works. No proxy, no wrapper script, no
  per-request flags.
- **In-progress fork.** Replace the workflow of
  `cd ../my-fork && npm pack && cd back && npm install ../my-fork/...tgz`
  with `"my-fork": "git+https://github.com/u/r.git#main"` in
  `package.json`. Push to the fork, run `guroku install`, done. The
  lockfile pins the commit SHA so collaborators get exactly your tree.
- **Vuln in a transitive dep.** A flaw in `ms@2.0.0` two layers down
  used to mean either waiting for the parent to update or vendoring a
  fork. Now:
  ```json
  { "overrides": { "ms": "2.1.3" } }
  ```
  pins it. The next `guroku install` rewrites the lockfile and the
  patched version is installed everywhere it appears in the graph.
- **CI hardening.** `guroku audit && deploy.sh` is the one-liner. The
  build fails closed on new advisories.

## Breaking changes

0.5 is mostly opt-in: existing `package.json` and `guroku.lock` files
from 0.4 install identically. The breakage is at the library API level.

- `guroku_core::resolver::Resolved` gained a field:
  ```rust
  pub local_source: Option<PathBuf>,
  ```
  Populated for `file:` and `git+` deps; `None` for registry deps. If
  you construct `Resolved` values by hand (tests, custom resolvers),
  you'll need to add the field. Pattern matches that didn't use `..`
  will need updating.
- `RegistryClient` internals changed to hold an `Npmrc` rather than a
  bare default-registry URL. The three public constructors —
  `RegistryClient::new()`, `::with_default_registry(url)`, and
  `::from_npmrc(npmrc)` — are unchanged. If you only call those, you
  are unaffected.

The CLI surface, lockfile schema, and on-disk store layout are all
backwards compatible.

## What didn't change

- Content-addressed store layout (`~/.guroku/store/v1/`).
- Strict `node_modules` topology — still no hoisting, still no
  phantom-dep access.
- Lockfile schema — `guroku.lock` from 0.4 is read without migration.
  New fields (`gitCommit`, `localSource`) are additive.
- Lifecycle script execution model and sandboxing behavior.
- All CLI subcommands shipped in earlier releases:
  `install`, `add`, `remove`, `update`, `list`, `why`, `run`, `exec`,
  `cache`, `store`, `prune`, `verify`. Flags and exit codes match 0.4.

## Known limitations

Things that parse but don't fully work, or that we punted on:

- **Path-keyed overrides.** Keys like `"foo > bar"` (override `bar`
  only when reached through `foo`) are accepted by the JSON parser but
  treated as a no-op during matching. Yarn's glob form
  (`"**/foo": "..."`) likewise parses without effect. Flat keys
  (`"ms": "2.1.3"`) work as expected.
- **Auth flavors beyond bearer tokens.** npm Basic auth
  (`_auth=base64...`) is not yet wired through. `${VAR}`
  interpolation in `.npmrc` values, and reading config from
  `npm_config_*` environment variables, are also deferred.
- **Git fanciness.** Submodules are not initialized. Sparse
  checkouts are not supported. If `git` prompts for credentials
  interactively, the install will hang — use a credential helper or
  embed the token in the URL.
- **Audit ergonomics.** No `--audit-level=<low|moderate|high|critical>`
  filter, no `--json` output, no `audit fix`. The exit-code-on-any
  behavior is intentional for CI; richer ergonomics ship in v0.6.
- **Workspace inter-dep linking.** Workspaces still install
  independently — a workspace package depending on a sibling
  workspace package will fetch the sibling from the registry rather
  than linking it locally. This is the headline item for v0.6 and is
  blocked on the resolver replacement.

## What's coming in v0.6

- **Workspace inter-dep linking** alongside the long-promised
  PubGrub-based resolver replacement. The current resolver is a
  greedy backtracker; PubGrub will give us better error messages and
  the structural hooks we need to link workspaces correctly.
- **Richer audit:** `--audit-level`, `--json`, and `audit fix` to
  rewrite `overrides` automatically.
- **v1.0 stability work:** locking down the library API, a written
  semver policy for the CLI, and an MSRV commitment.

## How to upgrade

See [`docs/migration/v0.4-to-v0.5.md`](migration/v0.4-to-v0.5.md) for
the step-by-step. The short version: update the binary, leave your
`package.json` and `guroku.lock` alone, drop in a `.npmrc` if you have
a private registry, and run `guroku install`.
