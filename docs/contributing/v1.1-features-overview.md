# v1.1 Features Overview (Contributor Tour)

This document is the contributor-facing tour of what shipped in guroku v1.1. It
is meant to be read alongside the code: each section points at the modules,
types, and tests that were touched, so a new contributor can orient themselves
without having to read every commit on the v1.1 branch.

If you are looking for the user-facing changelog, see `CHANGELOG.md` at the
repo root. This document is intentionally lower-level: it talks about *why*
each piece is shaped the way it is, and where to plug in next.

## 1. The bird's-eye list

The v1.1 release is a small, focused set of changes. Most of the surface area
is in two modules (`specs.rs` and `overrides.rs`) plus the resolver. The
headline items are:

- `DepSpec::Alias` variant — a new dependency-spec shape that records both a
  local name (the key under which the package appears in `node_modules`) and a
  registry name (the package the registry is asked for).
- `DepSpec` is now marked `#[non_exhaustive]` — adding further variants in
  later v1.x releases will not be a SemVer break for downstream code.
- `overrides::lookup_with_path` now honours both path-keyed entries
  (`"a > b > c"`) and glob entries, with a documented precedence ladder.
- `resolver::resolve_with_manifest_overrides` is the new preferred entry
  point. It threads the manifest's overrides table through the resolution loop
  rather than relying on the older free-function variant.
- Single-step backtracking in the resolver. When a transitive constraint
  conflicts with a previously chosen version, the resolver attempts a single
  upward substitution before giving up. Full PubGrub is deferred to v1.2.
- `Resolved::aliased_from` field — when a resolved package was reached via an
  alias, the original registry name is preserved on the resolved record so
  downstream consumers (the linker, the lockfile writer) can disambiguate.
- `ResolutionConflict.requested_by` now carries a path (a list of package
  names from the root manifest down to the conflicting dependency) instead of
  a single name. Error messages are correspondingly more useful.

None of these changes alter the CLI surface. `guroku --help` is byte-identical
to v1.0; the test `tests/cli_help_v1_1_no_new_subcommands.rs` enforces this.

## 2. Module map

This section walks each existing module that v1.1 touched. It is deliberately
written so you can cross-reference against the source while reading.

### `src/specs.rs`

- New `Alias` variant on `DepSpec`. The variant carries `local_name`,
  `registry_name`, and a `Range` (the version range to satisfy against the
  registry-name package).
- `classify` gained a new branch for the `npm:` prefix. A spec string of the
  form `npm:<registry-name>@<range>` parses into `DepSpec::Alias`. The local
  name comes from the manifest key, not from the spec string.
- `unparse` was extended to round-trip the new variant back into the
  `npm:<name>@<range>` form. The round-trip is exercised by
  `tests/manifest_alias_round_trip.rs`.
- `validate` is unchanged. Alias specs validate exactly like the existing
  registry-pinned specs once the registry name and range have been extracted.

### `src/overrides.rs`

This module saw the largest rewrite of v1.1. The pre-v1.1 implementation was a
single flat `HashMap<String, Range>` lookup. v1.1 replaces it with a
precedence ladder.

- `lookup_with_path(path: &[&str], package: &str) -> Option<&Range>` is the
  new lookup function. The precedence (from highest to lowest) is:
    1. Path-keyed exact entries (`"a > b > c"`).
    2. Glob entries that match the package name.
    3. Plain top-level entries (the v1.0 behaviour).
- `classify_entries(raw: &Map) -> Vec<OverrideEntry>` converts the raw
  manifest table into a vector of structured entries. This is what the
  resolver consumes; it lets the caller see the precedence-resolved view
  without re-implementing the ladder.
- New supporting types:
    - `OverrideEntry { source: OverrideSource, kind: OverrideKind, range: Range }`.
    - `OverrideSource` distinguishes which manifest field the entry came from
      (top-level `overrides` vs. `resolutions`).
    - `OverrideKind` is the parsed shape: `Plain(name)`, `Path(segments)`, or
      `Glob(pattern)`.

The four-way coverage matrix (path-keyed, glob, classify, v1-compat) lives in
`tests/overrides_path_keyed.rs`, `tests/overrides_glob.rs`,
`tests/overrides_classify_entries.rs`, and
`tests/overrides_v1_simple_compat.rs`.

### `src/resolver.rs`

- `resolve_with_manifest_overrides(manifest, registry) -> Result<Resolved>`
  is the new preferred entry point. It threads the manifest's overrides table
  through the resolution loop. The older `resolve` function is preserved for
  callers that build their override map manually, but new code should call
  `resolve_with_manifest_overrides`.
- `try_backtrack` is the new single-step substitution helper. See section 4
  below for the algorithm.
- The work queue now tracks the path from the root manifest to each pending
  dependency. This is what powers the path-bearing
  `ResolutionConflict.requested_by` errors and what feeds
  `lookup_with_path`.
- `ChosenEntry` (the resolver's internal record of a tentatively chosen
  version) gained three fields:
    - `metadata_name` — the registry name under which metadata was fetched.
      For non-alias specs this equals the local name. For aliases it is the
      registry name.
    - `original_range` — the range from the spec at the time of choice.
      Backtracking uses this to look up versions without re-deriving it from
      the queue.
    - `aliased_from` — `Option<String>`; `Some(registry_name)` when the entry
      was reached via an alias.
- `Resolved` (the user-visible result type) gained `aliased_from:
  Option<String>` for the same reason. The install pipeline and lockfile
  writer both branch on this field.

### `src/commands/install.rs`

- `install_from_resolution` now keys its `cas_paths` map by the local name of
  each resolved package, not by the registry name. For non-alias packages this
  is a no-op. For aliases it is the load-bearing change: the CAS lookup must
  agree with the linker, which writes into `node_modules/<local-name>/`.

### `src/commands/mod.rs`

- `into_linked_packages` now sets `LinkedPackage.name` from the local name on
  the resolved record. Previously it used the registry name, which was a bug
  in the alias path that only manifested at link time.

## 3. Why aliases need both `local_name` and `registry_name`

Aliases create a small impedance mismatch in the pipeline. Two stages disagree
about what "the package's name" is:

- The registry stage (resolver, metadata fetch) needs the *registry name*. The
  registry has never heard of the user's local alias; asking
  `registry.metadata("my-alias")` would 404. The resolver fetches metadata,
  picks versions, and does conflict detection under the registry name.
- The install stage (CAS extraction, linker, lockfile writer) needs the
  *local name*. The on-disk layout is `node_modules/<local-name>/`. The
  lockfile keys are local names. Anything downstream of resolution that
  touches the user's project sees only the local name.

The `ChosenEntry::metadata_name` field exists to bridge these two views inside
the resolver. When the resolver is mid-walk and needs to look up a previously
chosen version (during backtracking, see section 4), it indexes by
`metadata_name`. When the resolver finally produces `Resolved` records, it
re-keys by local name and stashes the registry name in `aliased_from`.

You can think of `aliased_from` as the resolver telling the rest of the
pipeline: "this is the local name; here's the registry name in case you need
it." The lockfile writer uses it to record the resolved tarball URL under the
correct key. The install pipeline ignores it (CAS keys are content-addressed,
not name-addressed). The linker ignores it (it only sees local names).

## 4. The single-step backtracking algorithm

The full algorithm and its proof-sketch are in
`docs/internals/single-step-backtrack.md`. The summary, for orientation:

When the resolver is processing a new dependency edge and discovers that the
new range conflicts with a version already chosen for that package, it does
not immediately raise `ResolutionConflict`. Instead, it attempts a single
substitution:

1. Find the highest version of the package that satisfies *both* the new
   range and the original range under which the previous version was chosen.
2. If such a version exists, substitute it for the chosen version in place.
   Do not re-walk the transitive dependencies of the substituted package.
3. If no such version exists, raise `ResolutionConflict` with a path-bearing
   `requested_by`.

The "do not re-walk" step is what makes this *single-step*. Re-walking would,
in the worst case, cascade and require something like full PubGrub to keep
the search bounded. By restricting the substitution to versions that satisfy
the original range, we guarantee that the previously walked transitive
dependencies are still valid: any version satisfying the original range has
the same dependency shape modulo the package's own SemVer guarantees, which
we trust.

This covers the common diamond case (root depends on A and B; A and B both
depend on C, with overlapping but distinct ranges) without any of the
machinery PubGrub would require. It does *not* cover cases where the
substitution itself introduces a new transitive conflict; those still raise
`ResolutionConflict`.

## 5. Why we ship single-step instead of full PubGrub

Full PubGrub is the right long-term answer. v1.2 is scheduled to do it. v1.1
ships single-step because the gap between "what we have" and "PubGrub
integrated" is larger than it looks:

- **A range-arithmetic adapter from `node_semver::Range` to
  `pubgrub::range::Range<V>`.** The two range types are not isomorphic.
  `node_semver` allows OR-of-AND ranges with prerelease tag rules that
  `pubgrub::range::Range` does not directly model. Writing the adapter is
  straightforward in the common case but has long-tail edge cases around
  prerelease, build metadata, and `||` separators.
- **A blocking-async bridge so the synchronous `DependencyProvider` trait
  can call our async `RegistryClient`.** PubGrub's solver loop is sync. Our
  `RegistryClient` is async (it has to be: it batches HTTP, reads from a
  shared cache, and respects rate limits). Bridging requires either a
  thread-pool plus `block_on`, or a parallel sync API that fans out to the
  async one. Neither is bad; both are work.
- **A migration plan for the conflict reports.** PubGrub's "incompatibility"
  derivations are richer than our `ResolutionConflict`: they form a tree of
  causes, not a single path. Our error printer would need to learn how to
  render that tree, and our test fixtures would need to be regenerated.

That is a v1.2 project. v1.1 ships the conservative path so users get the
diamond-fix value now; v1.2 will replace `try_backtrack` with the PubGrub
solver and (if all goes well) delete a fair amount of the resolver's BFS
loop in the process.

## 6. Tests added in v1.1

The v1.1 test set is intentionally narrow. It covers each new code path with
at least one focused test, plus a small number of regression-style tests that
pin behaviour we do not want to change.

- `tests/specs_alias_classify.rs`, `tests/specs_alias_unparse.rs`,
  `tests/specs_alias_non_exhaustive.rs` — three files exercising
  `DepSpec::Alias`. The non-exhaustive test is a compile-fail check that
  matches without a wildcard arm break.
- `tests/overrides_path_keyed.rs`, `tests/overrides_glob.rs`,
  `tests/overrides_classify_entries.rs`,
  `tests/overrides_v1_simple_compat.rs` — the four-way coverage of the new
  overrides module. Path-keyed and glob test their respective ladder rungs;
  `classify_entries` tests the public structured view; the v1-compat test
  pins that pre-v1.1 manifests still resolve identically.
- `tests/manifest_alias_round_trip.rs` — manifest persistence: parse,
  unparse, parse again, assert equality.
- `tests/error_resolution_path.rs` — pins the path-bearing conflict format.
  The test fixture is a small manifest that produces a known conflict; the
  test asserts the formatted error string contains the full path.
- `tests/resolver_backtracks_simple_diamond.rs` — the headline single-step
  backtracking case.
- `tests/resolver_no_backtrack_when_compatible.rs` — pins that we do *not*
  backtrack when the new range is already satisfied. (This was a bug during
  development.)
- `tests/resolver_alias_routes_to_real_name.rs` — pins that an alias spec
  causes metadata to be fetched under the registry name.
- `tests/cli_help_v1_1_no_new_subcommands.rs` — pins that the CLI surface is
  unchanged. If you add a subcommand in v1.x without intending to, this test
  fails first.

## 7. What v1.1 explicitly punted

These are tracked. They are not bugs. They are deferred features.

- **Full PubGrub.** Targeted for v1.2. See section 5.
- **Aliases in peer/optional deps.** v1.1 supports `npm:` aliases in
  `dependencies` and `devDependencies` only. Peer and optional deps are
  parsed but reject the `Alias` variant. Targeted for a later v1.x.
- **Aliases pointing at file:/git+ specs.** v1.1 only supports aliases that
  resolve against the registry. Aliasing a `file:` or `git+` spec is rejected
  at parse time. Targeted for a later v1.x.
- **Wildcards in path-keyed override paths.** Patterns like `"a > * > b"`
  are not supported; only literal segment paths are. The lookup function
  treats `*` as a literal package name (which will of course never match).
  Adding wildcard segments is a small change in `match_path` (see section 8).
- **Richer globs in resolutions.** Patterns like `pkg/**/foo` and
  `*-helper` are not supported. v1.1 globs are simple prefix/suffix
  patterns evaluated by `match_glob`. Switching to a real glob crate is a
  small change but a SemVer-relevant one (it expands the language).
- **Negation patterns / OR-patterns.** No `!pkg`, no `(a|b)`. Out of scope
  for v1.x; would be revisited if and when we ship a richer override DSL.

## 8. Where to extend next

If you are picking up a v1.x feature, this is the rough map of where to
start. Each bullet names the module and the function that is most likely the
right entry point.

- **Full PubGrub** -> `src/resolver.rs`. Replace the BFS loop with
  `pubgrub::solver::resolve` driven by a custom `DependencyProvider`. The
  hard part is the range adapter (see section 5). Suggested staging: land
  the adapter as its own module first (`src/resolver/range_adapter.rs`),
  ship it behind a feature flag, then wire it into a parallel solver entry
  point before deleting `try_backtrack`.
- **Richer globs** -> `src/overrides.rs::match_glob`. Use the `globset`
  crate. The function is small and self-contained; the test is to extend
  `tests/overrides_glob.rs` with the new patterns. Be careful about
  precedence: `globset` patterns can overlap, and the precedence ladder
  (section 2) needs a documented tiebreak rule for that case.
- **Path wildcards** -> `src/overrides.rs::match_path`. Treat segments equal
  to `*` as wildcards. The current implementation walks segments
  pair-by-pair and short-circuits on inequality; the change is to add a
  branch for `*`. Extend `tests/overrides_path_keyed.rs`.
- **Aliases in peer deps** -> `src/specs.rs::validate` and the peer-dep
  consumer in `src/resolver.rs`. The parser already accepts the spec; the
  validation step rejects it. Removing the rejection is one line; the work
  is in deciding the resolver's behaviour for peer aliases (specifically:
  whose alias wins when two parents alias the same registry name to
  different local names?). Write the design doc before the code.
- **Aliases for file:/git+** -> `src/specs.rs::classify`. Currently the
  `npm:` branch only chains into the registry parser. The change is to
  allow `npm:<local>@<file:...>` and `npm:<local>@<git+...>`. Most of the
  work is in deciding the canonical form for unparse.

## 9. For future v1.x readers

This document is intended to grow as v1.x ships. Each minor release should
add a section here (or, if a release is large enough, its own
`vX.Y-features-overview.md` peer document) describing what landed and how it
fits with what came before. The goal is that a contributor onboarding in
(say) v1.5 can read v1.0 -> v1.1 -> ... -> v1.5 in order and arrive at a
working mental model of the codebase as it stands, without having to
reverse-engineer it from the diff history.

Concretely, when you ship a v1.x feature:

- Add a bullet to section 1 of the relevant overview doc summarising it.
- Add a module-map entry in section 2 for each module touched.
- If the feature has a non-obvious design rationale, add a "why" section
  near sections 3-5 of this doc's structure.
- If the feature explicitly punts something, add it to section 7.
- If the feature opens a new extension point, add it to section 8.

The point is layered history: the v1.0 doc explains the foundation; this
v1.1 doc explains what changed and why; future v1.x docs will continue the
chain. A contributor can read straight through and see how the codebase
evolved.
