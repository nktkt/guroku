# v1.0 Features Overview

A contributor-facing tour of what landed in guroku v1.0.

Unlike the 0.x feature drops, v1.0 is mostly about stability and
documentation rather than new behaviour. The resolver is the same
resolver. The CLI is the same CLI. The on-disk store is the same
store. What's new is the promise that those things will not change
casually -- and the scaffolding (rustdoc, prelude, benches, fences)
that lets us keep that promise.

If you're reading this because you want to land something in v1.x,
the most important section is "What v1.0 explicitly punted" near the
bottom. Everything there is fair game; nothing there is allowed to
break the stability commitment described in the rest of the doc.

---

## 1. The bird's-eye list

- Stability commitment for the lockfile, the Rust API, and the CLI.
- `guroku::prelude` module re-exporting the most-used types.
- Comprehensive crate-level rustdoc (quickstart, module map, MSRV).
- `GurokuError` marked `#[non_exhaustive]` for forward-compat.
- Windows binaries added to the release matrix.
- Criterion benchmark scaffolding under `benches/`.

That's it. No new subcommands, no new resolver, no new auth flow,
no new lockfile schema. If you were expecting a long list, the
length of this section is the point.

---

## 2. Module map

Items added or expanded in v1.0:

- `src/prelude.rs`
  - New public module re-exporting the most-used types so embedders
    can `use guroku::prelude::*;` instead of hand-picking imports.
  - Re-exports the public types embedders actually reach for:
    error type, manifest, lockfile, spec, version, registry client
    handle, resolver entry point.
  - Deliberately small. The prelude is meant to stay stable -- if
    you're tempted to add ten things, add one.

- `src/lib.rs`
  - Comprehensive top-level rustdoc: quickstart for both the CLI
    user and the embedder, a module map, the v1.0 stability
    commitment, the MSRV statement.
  - The expanded module list now mentions `prelude` alongside the
    existing `manifest`, `lockfile`, `resolver`, `store`, `cache`,
    `registry`, `integrity`, `spec`, `version`, `error`.
  - No code changes -- only doc comments and the new `pub mod
    prelude;` line.

- `benches/lockfile_parse.rs`
- `benches/manifest_parse.rs`
- `benches/spec_classify.rs`
- `benches/version_satisfies.rs`
  - Criterion bench scaffolding. The bodies are placeholders that
    exercise representative inputs; the real measurement bodies
    live alongside in helper modules so we can iterate on them
    without churning the bench entry points.
  - The point of v1.0 is that we have a baseline to compare future
    work against, not that we ship perfectly tuned benches today.

No other module gained or lost public items in v1.0.

## 3. What changed in `error.rs`

One attribute, one doc comment, zero variant changes:

```rust
/// Errors returned by guroku's public API.
///
/// This enum is `#[non_exhaustive]` as of v1.0. New variants may be
/// added in any v1.x release without a major version bump. Callers
/// matching on `GurokuError` MUST include a wildcard arm.
#[non_exhaustive]
pub enum GurokuError {
    // ... existing variants, unchanged ...
}
```

The forward-compat contract this encodes:

- We will not rename, remove, or change the payload of any existing
  variant in v1.x. Those are stable.
- We may add new variants in v1.x for new error conditions (a new
  registry auth scheme, a new lockfile parse failure mode, etc.).
- Downstream code that exhaustively matches `GurokuError` without
  a wildcard arm is incorrect under the v1.0 contract; the
  `#[non_exhaustive]` attribute makes this a compile error rather
  than a silent miss.

The `kind()` method's return enum is also stable: `ErrorKind` keeps
the same variants and the same `From<&GurokuError>` mapping. The
exhaustive `kind()` fence test (see Tests section) is what enforces
that.

## 4. What changed in `lib.rs`

Zero functional changes. Two large doc additions and one new line:

- Crate-level rustdoc covering:
  - **Quickstart -- CLI.** A four-line "install, init, add, install"
    transcript so a reader who lands on docs.rs can see what the
    binary actually does.
  - **Quickstart -- embedding.** A short example that loads a
    manifest, runs the resolver, and writes a lockfile, all using
    `guroku::prelude::*;`. This doubles as the smoke test for
    "does the prelude actually contain the things you need?" -- if
    the example stops compiling, the prelude is missing something.
  - **Module map.** One line per public module describing what it
    contains and when you'd reach for it.
  - **Stability commitment.** The text version of section 5 of this
    doc, plus a pointer to `docs/deprecation-policy.md` for how
    things leave the public API in v1.x.
  - **MSRV.** The current minimum supported Rust version, plus the
    bump policy: MSRV bumps are a minor-version event, not a patch
    event, and require an entry in `docs/MSRV.md`.
- New line: `pub mod prelude;`.

That's the complete diff. No re-exports moved, no items were
hidden, no items became `pub(crate)`.

## 5. What didn't change

This list is load-bearing. Each bullet is a thing the v1.0
stability commitment promises will not break under you in v1.x:

- **Every existing public type's signature.** Field order,
  visibility, `#[serde]` attributes, derived traits.
- **The CLI surface.** Subcommand names, flag names, flag short
  forms, help text headings, exit codes, the layout of the
  top-level `--help` output.
- **The on-disk store.** `~/.guroku/store/<algo>-<hash>/...` is
  the layout, and the algo is `sha512`. Nothing in v1.x will
  change either of those.
- **The lockfile schema.** `lockfileVersion: 1`, the field names,
  the field types, the canonical key ordering on serialization.
  Forward-compat on _reading_ is also pinned: an unknown field in
  a lockfile is preserved on round-trip, not rejected and not
  silently dropped.
- **The manifest schema.** Same forward-compat rule: unknown
  fields round-trip. Required fields stay required, optional
  fields stay optional.
- **Resolver semantics.** BFS, sticky-first, deterministic given
  the same inputs. Same tie-breaking, same conflict reporting.

If you are about to land a change that touches anything in this
list, stop and read `docs/deprecation-policy.md` first. There is
a process. The process exists.

## 6. Tests added in v1.0

The point of these tests is to be a fence, not a unit test in the
usual sense. They fail loudly when somebody accidentally breaks
the stability commitment. None of them test new behaviour --
they test that old behaviour is still the same.

- `tests/api_stability_re_exports.rs`
- `tests/api_stability_prelude.rs`
  - Compile-time fences against accidental API churn. The bodies
    are mostly `let _: fn(...) -> ... = ...;` lines that pin
    specific function signatures, plus `use` statements that pin
    specific paths. If a re-export disappears or changes shape,
    these tests fail to compile.

- `tests/lockfile_v1_compat.rs`
- `tests/lockfile_unknown_field.rs`
- `tests/lockfile_format_stability.rs`
  - Pin the lockfile schema and the forward-compat behaviour. The
    `_v1_compat` test loads a checked-in fixture and asserts the
    parsed shape. The `_unknown_field` test asserts that an
    unknown top-level and unknown per-package field both
    round-trip rather than getting dropped or rejected. The
    `_format_stability` test asserts byte-for-byte serialization
    of a known input -- key order, indentation, trailing newline.

- `tests/manifest_unknown_field.rs`
- `tests/manifest_full_round_trip.rs`
  - Pin the manifest schema. Same forward-compat rule as the
    lockfile: unknown fields survive a load + save cycle.
    `_full_round_trip` covers a kitchen-sink manifest with every
    documented field populated.

- `tests/cli_help_v1.rs`
- `tests/cli_subcommand_inventory.rs`
- `tests/cli_version_includes_v1.rs`
  - Pin the CLI surface. `_help_v1` snapshots `guroku --help`
    output. `_subcommand_inventory` enumerates the subcommands
    and asserts the set is exactly what v1.0 shipped with.
    `_version_includes_v1` asserts `guroku --version` reports a
    1.x version string in the documented format.

- `tests/version_v1_constants.rs`
  - Pins the public constants: `LOCKFILE_VERSION`,
    `DEFAULT_REGISTRY`, the cache path constants, the user-agent
    string format. Constants are part of the public API too.

- `tests/integrity_known_vector.rs`
  - Pins SHA-512 outputs against known vectors. If the integrity
    module ever silently changed algorithm or encoding, this
    catches it. The vectors are hand-checked and committed
    alongside the test.

- `tests/error_kind_classification.rs`
  - Exhaustive variant-by-kind fence. Builds one instance of
    every `GurokuError` variant, asserts the resulting `kind()`
    matches the documented mapping. The match in the test is
    deliberately exhaustive (no wildcard) so that adding a
    variant in v1.x without updating the table fails to compile.
    This is the one place we _do_ exhaustively match
    `GurokuError` -- inside guroku itself, with a known set of
    variants.

- `tests/cache_paths_v1.rs`
  - Pins the `~/.guroku/...` layout. Asserts that the helpers
    return the documented paths and that none of the names have
    drifted (`store/`, `tarballs/`, `metadata/`, `tmp/`).

These tests live alongside the existing `tests/` integration
tests and run as part of `cargo test`. They are not gated behind
a feature flag. If they fail, the right answer is almost always
"don't make that change," not "update the fixture."

## 7. CI changes

`release.yml` gained Windows targets in the build matrix:

- `x86_64-pc-windows-msvc`
- `aarch64-pc-windows-msvc`

The Linux and macOS targets are unchanged. The release artifact
naming follows the existing `guroku-<version>-<target>.<ext>`
pattern; Windows builds produce `.zip` archives instead of
`.tar.gz` so Windows users can extract them with the built-in
shell.

Three new workflows complement the existing `ci.yml` and
`audit.yml`:

- `.github/workflows/semver-checks.yml`
  - Runs `cargo semver-checks` against the previous release.
    Fires on PRs that touch `src/` or `Cargo.toml`. Failing this
    check is not automatic grounds for blocking a PR (some
    breakage is intentional and gets a major bump), but it does
    require an explicit ack in the PR description.

- `.github/workflows/cross-platform-test.yml`
  - Runs the full test suite on Linux, macOS, and Windows. The
    existing `ci.yml` runs Linux only on every push; this
    workflow runs the cross-platform matrix on PRs and on a daily
    schedule against `main`.

- `.github/workflows/bench-baseline.yml`
  - Runs the criterion benches on `main` and uploads the results
    so future PRs have a baseline to compare against. This
    workflow does not gate PRs -- it just collects numbers.

The pre-existing `audit.yml` (cargo-audit, supply-chain checks)
and `ci.yml` (fmt, clippy, test, doc) are unchanged.

## 8. What v1.0 explicitly punted

Everything in this list is on the v1.x roadmap. None of it is
allowed to break the v1.0 stability promise:

- **PubGrub-based resolver.** The BFS sticky-first solver remains
  the default in v1.0. A PubGrub experiment may land behind a
  feature flag in v1.x, but switching the default would change
  resolution outcomes in edge cases, which is exactly what the
  stability commitment forbids without a major bump.

- **Workspace inter-dep linking.** Workspaces are still resolved
  per-member with no cross-member symlinking. The plumbing for
  shared lockfiles is in `lockfile.rs` already; the install-side
  linking is the missing piece.

- **`--audit-level`, `--json`, `audit fix`.** The `audit`
  subcommand exists and reports vulnerabilities. The output
  format is human-readable only, the threshold is hard-coded,
  and there is no auto-fix. All three are additive and can land
  in v1.x without breaking anything.

- **npm Basic auth in `.npmrc`.** Bearer tokens (the modern
  scheme) are supported. Basic auth (the legacy scheme) is not.
  Adding it is additive.

- **Sandboxed lifecycle scripts.** Lifecycle scripts run in the
  same process tree as `guroku install`, with no sandboxing
  beyond what the OS gives you. Sandboxing -- whether via
  seccomp, sandbox-exec, AppContainer, or a uniform shim -- is a
  v1.x project.

If your contribution is in this list, great. If your
contribution is _not_ in this list and is also _not_ in section
5 ("What didn't change"), it's probably fine -- but check with
a maintainer first if you're unsure which side of the line it
lands on.

## 9. For future contributors

A few signposts so you know which doc to open next:

- **Want to add to the public API?**
  Read `docs/internals/api-design.md` first. It covers the
  bar for adding to `prelude`, the rules for re-exports, the
  conventions for new modules, and how to write the rustdoc
  for a new public type so it matches the rest of the crate.

- **Want to deprecate something?**
  Read `docs/deprecation-policy.md`. The summary is: nothing
  leaves the public API in v1.x. You add `#[deprecated]` with
  a clear `since` and `note`, you update the rustdoc, you add
  a CHANGELOG entry, and the actual removal waits for v2.0.
  But read the doc -- there are wrinkles for things like
  re-exports and trait methods.

- **Want to bump MSRV?**
  See `docs/MSRV.md`. MSRV bumps are a minor-version event,
  not a patch-version event. They require a justification in
  the PR description (what feature, why it's worth the bump),
  a CHANGELOG entry, and an update to the badge in the README.

- **Want to add a benchmark?**
  Drop a new file in `benches/`, register it in `Cargo.toml`,
  and follow the naming pattern of the existing four. The
  bench-baseline workflow will pick it up automatically.

- **Want to add a stability fence test?**
  Drop a new file in `tests/` with a name that says what it
  pins. The convention in v1.0 is `<area>_<what>_v1.rs` or
  `<area>_<what>.rs` -- consistency with the existing names is
  more important than strict adherence to either pattern.

Welcome to v1.0. The most useful thing you can do as a new
contributor is read sections 5 and 8 of this doc carefully:
section 5 tells you what's off-limits, and section 8 tells you
where the open work is.
