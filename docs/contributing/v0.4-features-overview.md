# v0.4 features overview

This is a contributor-facing tour of what landed in guroku v0.4. It is meant
for someone who has not been following the milestone day-to-day and now needs
to touch the code. Read it once before opening the source tree; it will make
the diff much easier to navigate.

The focus of v0.4 was *catching up to npm's surface area* in the areas that
real-world packages assume exist: lifecycle scripts, a `run`/`exec` runner,
workspace discovery, `node_modules/.bin/` shims, and `.npmrc` reading. None
of these features add new resolver behaviour; they all sit on top of the
v0.3 resolver+linker pipeline.

## 1. The bird's-eye list

- **Lifecycle scripts** — `preinstall`, `postinstall`, and `prepare` are now
  invoked at install time. `preinstall` runs once on the root before the
  resolver. `postinstall` runs per-package after linking. `prepare` runs on
  the root after `postinstall` completes.
- **`guroku run` and `guroku exec`** — `run` invokes a script from the
  root manifest's `scripts` table. `exec` resolves a binary from
  `node_modules/.bin/` (or `PATH` as a fallback) and execs it.
- **`guroku workspaces` (discovery only)** — lists workspace members
  resolved from the root manifest's `workspaces` field. v0.4 does *not* link
  workspaces into each other; that is a v0.5 task (see section 7).
- **`node_modules/.bin/` shims** — direct dependencies that declare a `bin`
  entry are symlinked into `node_modules/.bin/` after linking. Transitive
  bins are deliberately not exposed.
- **`.npmrc` reading** — guroku now reads `.npmrc` from the project root and
  the user's home directory, with project taking precedence. v0.4 only
  consumes `registry`, scoped registries (`@scope:registry`), and
  `_authToken` *for reading* (not yet for outgoing requests).

## 2. Module map

### `src/scripts.rs` — shell runner

This module owns the "spawn a shell, run a string, stream its output" path.
The public surface is small: `run_in(dir, script, env)` for a single script
and `run_lifecycle(pkg_dir, name)` for the conventional named hooks. On Unix
it shells out to `/bin/sh -c`; on Windows it uses `cmd /C`. The runner
inherits stdio so the user sees script output live, and propagates the exit
status as a `GurokuError::ScriptFailed`. There is intentionally no sandboxing
or timeout; matching npm's behaviour is the point.

### `src/npmrc.rs` — config reader

A small parser for the subset of `.npmrc` we care about. It walks the
candidate locations (`./.npmrc`, `$HOME/.npmrc`), parses each into a
`BTreeMap<String, String>`, and merges with project-overrides-home
precedence. Public accessors are `registry()`, `scoped_registry(scope)`, and
`auth_token(registry_url)`. The auth token accessor is wired but unused by
the registry client in v0.4 (see section 7).

### `src/workspaces.rs` — glob-based discovery

Given the root manifest, this module expands the `workspaces` field into a
list of `WorkspaceMember { path, manifest }`. Globs are resolved with the
`glob` crate; each match must contain a `package.json`, otherwise it is
skipped with a warning. Results are sorted by path for deterministic output.
Discovery is the entire job — there is no inter-workspace symlinking here.

### `src/commands/run.rs` / `exec.rs` / `workspaces.rs` — CLI dispatchers

Three thin command handlers that sit between `clap` and the modules above.
`run.rs` looks up the requested script in the root manifest and hands off to
`scripts::run_in`. `exec.rs` resolves the requested binary against
`node_modules/.bin/`, falling back to `PATH`, and execs it with the
remaining argv passed through. `workspaces.rs` calls
`workspaces::discover` and prints a table of members. None of these handlers
contains business logic; they exist to keep `main.rs` shallow.

## 3. Where the install pipeline grew

`src/commands/install.rs` is the spine of the install command. In v0.3 it
read the manifest, resolved, and linked. In v0.4 it now wraps that core
with two lifecycle phases:

```rust
pub fn run(args: InstallArgs) -> Result<(), GurokuError> {
    let manifest = Manifest::load(&args.root)?;

    // NEW in v0.4: root-level preinstall before any resolution work.
    run_root_scripts(&manifest, &args.root, &["preinstall"])?;

    let graph = resolver::resolve(&manifest, &args.root)?;
    let linked = linker::populate_node_modules(&graph, &args.root)?;

    // NEW in v0.4: per-package postinstall, in dependency order.
    // `linked` is already topologically sorted by the linker.
    run_per_package_postinstall(&linked)?;

    // NEW in v0.4: root-level prepare after the tree is fully usable.
    run_root_scripts(&manifest, &args.root, &["prepare"])?;

    Ok(())
}
```

Two helpers are new and live alongside this function:

- `run_root_scripts(manifest, root, names)` — looks each name up in
  `manifest.scripts` and runs the ones present, in the order given.
- `run_per_package_postinstall(linked)` — iterates linked packages,
  invoking `postinstall` only on those whose own manifest declares one.

The linker's own behaviour did not change here; the install command is the
only caller of the lifecycle helpers.

## 4. Manifest schema additions

`src/manifest.rs` gained three new fields on the deserialised `Manifest`
struct. All three are typed as `Option<...>` because a real-world
`package.json` may omit any of them, and we want to distinguish "absent"
from "empty".

```rust
pub struct Manifest {
    // ... existing fields ...
    pub scripts: Option<BTreeMap<String, String>>,
    pub bin: Option<BinField>,
    pub workspaces: Option<WorkspacesField>,
}
```

Two of the fields use small enums to deal with shape variants from the
ecosystem:

```rust
#[derive(Deserialize)]
#[serde(untagged)]
pub enum BinField {
    /// `"bin": "./cli.js"` — implies one entry named after the package.
    Single(String),
    /// `"bin": { "name": "./cli.js", ... }` — explicit map.
    Map(BTreeMap<String, String>),
}

#[derive(Deserialize)]
#[serde(untagged)]
pub enum WorkspacesField {
    /// `"workspaces": ["packages/*"]` — npm shape.
    List(Vec<String>),
    /// `"workspaces": { "packages": [...] }` — pnpm/yarn shape.
    Object { packages: Vec<String> },
}
```

The two normaliser helpers expose a single shape to the rest of the
codebase, so callers never branch on the enum:

- `Manifest::bin_entries(&self) -> BTreeMap<String, String>` — returns
  `{name -> path}`. For `BinField::Single(p)`, the name is `self.name`.
- `Manifest::workspace_globs(&self) -> Vec<String>` — returns the glob
  list regardless of which shape the manifest used.

If you are adding a new caller, prefer the helpers; keep the enums
encapsulated.

## 5. Linker additions

`src/linker.rs` gained a small amount of public surface to support
`node_modules/.bin/`.

`LinkedPackage` (the per-package result type returned by the linker) now
carries the package's bin entries:

```rust
pub struct LinkedPackage {
    pub name: String,
    pub version: Version,
    pub path: PathBuf,
    pub is_direct_dep: bool,        // already existed
    pub bin_entries: BTreeMap<String, String>, // NEW in v0.4
}
```

`bin_entries` is populated from `Manifest::bin_entries()` at link time, so
the linker does not have to re-parse manifests later.

`populate_bin_dir` is a new public function:

```rust
pub fn populate_bin_dir(
    node_modules: &Path,
    linked: &[LinkedPackage],
) -> Result<(), GurokuError>;
```

It is called once from `populate_node_modules` after all packages have been
linked. It walks `linked`, filters to `is_direct_dep == true`, and for each
direct dep creates a symlink (or `.cmd` shim on Windows) in
`node_modules/.bin/` for every entry in that package's `bin_entries`.

The "direct deps only" rule is intentional and matches npm. Transitive
dependencies' bins are reachable by their own packages but should not be
exposed at the top level. If two direct deps declare the same bin name, the
later one wins and we log a warning — again matching npm's pragmatic
behaviour.

## 6. Error surface additions

Six new variants on `GurokuError` (in `src/error.rs`). The thread of these
errors is "things that can go wrong in the new v0.4 surfaces":

- `ScriptNotFound { name }` — `guroku run <name>` was invoked but no such
  script exists in the root manifest.
- `ScriptFailed { name, status }` — a lifecycle or `run` script exited
  non-zero. `status` is the raw `ExitStatus`.
- `BinNotFound { name }` — `guroku exec <name>` could not resolve `<name>`
  in `node_modules/.bin/` or `PATH`.
- `WorkspaceGlobError { pattern, source }` — the `workspaces` field
  contained a glob that failed to compile or matched nothing usable.
- `NpmrcParseError { path, line }` — a line in `.npmrc` was malformed.
- `BinShimError { name, source }` — creating a symlink (or Windows `.cmd`
  shim) in `node_modules/.bin/` failed.

All six round-trip through `Display` with messages that name the offending
input (script name, bin name, glob pattern, etc.) so users can act without
re-running with `--verbose`.

## 7. What v0.4 explicitly punted

These were considered and *deliberately* left for later. If you find
yourself wanting one of these mid-task, stop and check the issue tracker
before implementing — there is likely an open design discussion.

- **Workspace inter-dep linking** — v0.4 only *discovers* workspaces. It
  does not symlink workspace A into workspace B's `node_modules/`. That is
  the headline v0.5 feature.
- **`_authToken` on outgoing requests** — `npmrc::auth_token` is wired and
  tested, but the registry client does not yet attach it to outgoing
  fetches. Slated for v0.5 alongside private-registry support.
- **`npm_*` env vars during scripts** — npm exposes a wide surface of
  `npm_package_*`, `npm_config_*`, etc. variables to scripts. v0.4 does
  not. Tracked for a v0.4.x point release.
- **`${VAR}` interpolation in `.npmrc`** — npm expands `${HOME}`-style
  references inside `.npmrc` values. v0.4 reads them literally. Also a
  v0.4.x point-release item.
- **`guroku dlx`** — the `npx`-equivalent "fetch and run" command is not in
  v0.4. Likely v0.4.x.

## 8. Tests added

The integration test suite under `tests/` grew alongside each module. If
you change one of these areas, run the matching file first; full-suite
runs are slower because they each build a tiny package fixture.

- `tests/scripts_*.rs` — covers `scripts::run_in` and `run_lifecycle`,
  including non-zero-exit propagation and stdio inheritance.
- `tests/npmrc_*.rs` — `.npmrc` parsing, project-over-home precedence,
  scoped registry lookups.
- `tests/workspaces_*.rs` — discovery against both `List` and `Object`
  shapes, missing `package.json` warnings, deterministic ordering.
- `tests/cli_run_*.rs` — `guroku run` end-to-end including
  `ScriptNotFound`.
- `tests/cli_exec_*.rs` — `guroku exec` resolution order
  (`node_modules/.bin/` before `PATH`) and argv pass-through.
- `tests/linker_bin_*.rs` — `populate_bin_dir` symlink creation,
  direct-deps-only rule, name-collision behaviour.
- `tests/manifest_bin_entries.rs` — `bin_entries()` and
  `workspace_globs()` normalisation across both shape variants.

A handful of smaller files (`tests/install_lifecycle_*.rs`) cover the
install-pipeline integration in section 3; they are slower and live behind
the default `#[ignore]` flag for individual `cargo test` runs but execute
in CI.

## 9. Where to extend next

Concrete pointers if you are picking up follow-up work. Each line names the
nearest module so you can start reading without grepping.

- **Workspace inter-dep linking** — touch `src/resolver.rs` (so the
  resolver knows that workspace members satisfy each other's deps) and
  `src/linker.rs` (so the linker creates the right symlinks). The
  workspace discovery in `src/workspaces.rs` is already enough input;
  do not duplicate it in the resolver.
- **Auth on outgoing requests** — `src/registry.rs` is where outgoing HTTP
  is built. `src/npmrc.rs::auth_token` is the existing accessor; wire it
  into the request builder there. Watch out for the registry-URL
  normalisation (trailing slash, scheme); the accessor expects a canonical
  form.
- **`npm_*` env vars during scripts** — `src/scripts.rs::run_in` is the
  single chokepoint where the command's environment is assembled. Build
  the `npm_package_*`/`npm_config_*` map next to the existing `env`
  argument and merge before spawning. The manifest is already in scope at
  every caller.

For anything else, start at the module map in section 2 and follow the
imports — v0.4's surface is shallow on purpose.
