# v0.5 features overview

This is a contributor-facing tour of what landed in guroku v0.5. It is meant
for someone who has not been following the milestone day-to-day and now
needs to touch the code. Read it once before opening the source tree; it
will make the diff much easier to navigate.

The focus of v0.5 was *broadening what guroku can install from and resolve
through*: bearer-auth on outgoing registry requests, scoped-registry
routing, non-registry dependency sources (`file:` and `git+`), the
`overrides` / `resolutions` resolver hooks, and a first-pass `audit`
subcommand. The resolver and linker pipelines from v0.3/v0.4 are still the
backbone; v0.5 adds new pre- and post-processing around them rather than
replacing them.

If you are coming from v0.4: the four features in section 1 are the entire
diff at the user level. Everything else (the new modules, the changes to
existing modules, the new error variants) exists to support those four.

## 1. The bird's-eye list

- **Bearer-auth + scoped-registry routing in `RegistryClient`** — the
  client now consults an `Npmrc` for both *which* registry to talk to (per
  scope) and *what auth header* to attach. The accessor `npmrc::auth_token`
  that was wired-but-unused in v0.4 is now used.
- **`file:` and `git+` dependency support** — a dep version string is no
  longer assumed to be a semver range. It is classified into a `DepSpec`
  (registry / file / git) up front, and non-registry specs bypass the CAS
  fetch path entirely.
- **`package.json#overrides` / `resolutions`** — the resolver now consults
  a flat-name override table before contacting the registry. The two field
  names are accepted as synonyms (npm uses `overrides`, yarn uses
  `resolutions`); see section 5 for the punted glob/path-keyed forms.
- **`guroku audit` subcommand** — POSTs the locked dependency tree to the
  configured registry's advisories endpoint and prints the response. No
  `--json`, no `audit fix`, no `--audit-level` filter; see section 5.

## 2. Module map

### `src/specs.rs` — DepSpec classifier

This module owns the "given a raw version string from `package.json`, what
*kind* of dependency is this?" decision. The public surface is the
`DepSpec` enum and the `DepSpec::parse(name, version)` constructor. Three
variants:

```rust
pub enum DepSpec {
    Registry { name: String, range: VersionReq },
    File     { name: String, path: PathBuf },
    Git      { name: String, url: String, reference: Option<String> },
}
```

Classification is purely lexical: a value beginning with `file:` is a
`File`, a value beginning with `git+` (or matching the
`git://`/`git@host:path` shapes we whitelist) is a `Git`, and everything
else falls through to `Registry` and is parsed as a semver `VersionReq`.
The classifier intentionally does no I/O — it does not stat the path or
contact the git remote — so it is cheap to call from anywhere in the
resolver. Validation of the path's existence happens later, in
`commands::install`.

### `src/git.rs` — subprocess-driven git clone

A small wrapper around the `git` binary. The public surface is
`ensure_cloned(url, reference, dest) -> Result<PathBuf, GurokuError>`.
v0.5 deliberately shells out to the user's `git` rather than linking
`libgit2`: it is shorter to write, the binary is universally present in
the environments we care about, and matching every git transport's auth
behaviour ourselves is not in scope for this milestone.

The implementation runs `git clone --depth 1` for the default branch and
`git clone` followed by `git checkout <ref>` when a reference is supplied.
Output is captured (not streamed) so that a failed clone produces a single
`GitCloneFailed` error containing both stderr and the exit status. The
function is idempotent on `dest`: if the directory already exists and
contains a `.git`, the clone is skipped.

### `src/audit.rs` — POST to advisories endpoint

This module assembles the audit request body, POSTs it via
`RegistryClient::http_post_json`, and renders the response. The request
shape matches npm's `/-/npm/v1/security/advisories/bulk` body: a map from
package name to the list of versions present in the install. The response
is parsed into a `Report { advisories: Vec<Advisory>, summary: Summary }`
and printed via `print_report(&Report, &mut dyn Write)`. The writer
parameter is there so we can re-target it later (see section 8); v0.5
always passes `io::stdout`.

### `src/overrides.rs` — flat-name override lookup

A self-contained table type. `OverrideTable::from_manifest(manifest)`
merges the two manifest fields into a single `BTreeMap<String, String>`
(see section 3 for the precedence rule). The lookup function is
intentionally narrow:

```rust
pub fn lookup(&self, name: &str) -> Option<&str>;
```

Just the bare package name — no resolution path, no glob matching. Both
of those are explicitly punted to a later milestone (section 5). The
return type is the *raw version string* from the override map, so
`overrides.rs` does not need to know about `DepSpec`; the resolver
re-classifies the result through `DepSpec::parse`.

### `src/commands/audit.rs` — CLI handler

The thin command handler that sits between `clap` and `audit.rs`. It
loads the manifest, walks the resolved graph (re-running the resolver if
no lockfile is present), constructs the bulk request body, calls
`audit::run(&client, body)`, and feeds the result into
`audit::print_report`. No business logic lives here; it exists to keep
`main.rs` shallow, the same pattern as the v0.4 command handlers.

## 3. Where existing modules grew

### `src/registry.rs`

`RegistryClient` now holds an `Npmrc` rather than a single registry URL:

```rust
pub struct RegistryClient {
    http: HttpClient,
    npmrc: Npmrc,
}
```

Two new accessors do the routing and auth work:

- `registry_for(&self, name: &str) -> &str` — given a package name,
  returns the registry URL to use. For a scoped name like `@acme/foo` it
  consults `npmrc.scoped_registry("@acme")` and falls back to the default
  registry; for an unscoped name it returns the default directly.
- `auth_for(&self, url: &str) -> Option<&str>` — given a registry URL,
  returns the bearer token to attach (if any). It normalises the URL
  before lookup so trailing-slash and scheme variants do not miss.

Every outgoing request inside `RegistryClient` now goes through these two
helpers; there is no longer a code path that uses a hard-coded URL or
skips auth. `http_post_json` is also new on the client; it is the
transport used by `audit.rs`.

Basic-auth and `${VAR}` interpolation in npmrc are still punted; only
bearer tokens (`_authToken`) are honoured (section 5).

### `src/resolver.rs`

The resolver previously walked `BTreeMap<String, String>` of name-to-range
pairs. It now walks `Vec<DepSpec>` instead — the classification happens
once at the manifest boundary and the resolver branches on the variant:

- `DepSpec::Registry` — unchanged; goes through the registry client.
- `DepSpec::File` — read the path's `package.json`, treat that as the
  resolved unit, recurse into its deps. No registry call.
- `DepSpec::Git` — call `git::ensure_cloned`, then proceed as for
  `File` against the cloned working tree.

`Resolved` (the resolver's per-package result type) gained one field:

```rust
pub struct Resolved {
    pub name: String,
    pub version: Version,
    pub dist: Option<Dist>,        // existed
    pub local_source: Option<PathBuf>, // NEW in v0.5
}
```

`local_source` is `Some(path)` for `File` and `Git` deps and `None` for
registry deps. Downstream code (the install command, the linker bridge)
uses `local_source.is_some()` to skip CAS work — see the install changes
below.

The new public entry point is:

```rust
pub fn resolve_with_overrides(
    manifest: &Manifest,
    overrides: &OverrideTable,
    client: &RegistryClient,
) -> Result<Graph, GurokuError>;
```

Internally it consults `overrides.lookup(name)` before each registry
fetch; if the override is present the result is re-classified through
`DepSpec::parse` and the override path is taken. The plain `resolve`
function still exists and is implemented as
`resolve_with_overrides(manifest, &OverrideTable::empty(), client)`.

### `src/manifest.rs`

Two new typed fields:

```rust
pub struct Manifest {
    // ... existing fields ...
    pub overrides:   Option<BTreeMap<String, String>>,
    pub resolutions: Option<BTreeMap<String, String>>,
}
```

Both are `Option<BTreeMap<...>>` for the same "absent vs empty" reason
called out for the v0.4 fields. The merge precedence — `overrides` wins
over `resolutions` on key collision — is enforced by
`OverrideTable::from_manifest` rather than the deserialiser, so the
manifest type stays a faithful mirror of the JSON shape.

Path-keyed override entries (`"foo > bar": "1.0.0"`) and glob resolutions
(`"**/foo": "..."`) are accepted at the JSON layer (the value is just a
string) but ignored by `OverrideTable`; see section 5.

### `src/cli.rs`

One new subcommand variant:

```rust
pub enum Command {
    // ... existing variants ...
    Audit(AuditArgs),
}
```

`AuditArgs` is currently empty (no flags). The dispatcher in `main.rs`
forwards to `commands::audit::run`. The flag surface is intentionally
small; `--audit-level`, `--json`, and `audit fix` are all punted
(section 5).

### `src/commands/install.rs`

Two changes, both small:

- The CAS-fetch loop now filters by `local_source.is_none()`. Packages
  with a `local_source` are already on disk (either because the user
  pointed at them with `file:` or because `git::ensure_cloned` placed
  them there) and have no tarball to fetch. Skipping them avoids an
  unnecessary registry round-trip and a pointless cache write.
- The resolve call now goes through `resolve_with_overrides`, with the
  `OverrideTable` built from the root manifest. There is no command-line
  override mechanism in v0.5; the table is always manifest-derived.

The lifecycle-script wrapper from v0.4 is unchanged. Lifecycle scripts
fire for `file:` and `git+` deps just as they do for registry deps.

### `src/commands/mod.rs`

`into_linked_packages` (the bridge that turns a resolver `Graph` into the
linker's `Vec<LinkedPackage>` input) now honours `local_source`. When
`local_source` is `Some`, the linker is told to source files from that
path rather than from the CAS. The linker itself did not change; it
already accepts an arbitrary source directory.

## 4. Errors added

Four new variants on `GurokuError` (in `src/error.rs`):

- `GitCloneFailed { url, status, stderr }` — `git::ensure_cloned` ran
  `git clone` (or `git checkout`) and got a non-zero exit. `stderr` is
  captured so users do not need to re-run with `--verbose`.
- `FileDepNotFound { name, path }` — a `file:` dependency pointed at a
  path that does not exist or does not contain a `package.json`. Raised
  by the resolver when it tries to read the local manifest.
- `AuditRequestFailed { status, body }` — the advisories endpoint
  returned a non-2xx response. The body is included verbatim because
  npm-compatible registries put the actionable error message there.
- `OverrideParseError { name, value }` — an entry in `overrides` /
  `resolutions` could not be classified by `DepSpec::parse`. The name and
  raw value are both included so the user can find the offending key.

All four round-trip through `Display` with messages that name the
offending input, matching the v0.4 convention.

## 5. What v0.5 explicitly punted

These were considered and *deliberately* left for a later milestone. If
you find yourself wanting one of these mid-task, stop and check the issue
tracker before implementing — there is likely an open design discussion.

- **Path-keyed overrides** — entries of the form `"foo > bar": "1.0.0"`
  are parsed by serde (the JSON shape allows them) but ignored by
  `OverrideTable`. The lookup is by bare name only. Extending this is
  one of the cleaner follow-ups (section 8).
- **Glob `resolutions`** — yarn-style `"**/foo": "..."` is similarly
  parsed-and-dropped. Same reasoning.
- **Basic auth and `${VAR}` interpolation in npmrc** — only `_authToken`
  is honoured for outgoing requests. `_auth` (basic) and `${VAR}`
  expansion are still on the roadmap. The `auth_for` accessor is the
  single place to extend.
- **Git submodules / sparse checkouts** — `git::ensure_cloned` always
  does a plain clone (with `--depth 1` when no reference is requested).
  Submodules are not initialised; sparse checkouts are not configured.
  Real-world repos that depend on submodules will need to vendor.
- **`--audit-level`, `--json`, `audit fix`** — the audit subcommand has
  no flags. Severity filtering, machine-readable output, and the
  fix-and-rewrite-the-tree flow are all out of scope for v0.5.
- **Workspace inter-dep linking** — slipped from v0.4, again deferred.
  Now firmly the v0.6 headline. v0.5's resolver still does not treat
  workspace members as locally-rooted; `local_source` is only populated
  for `File` and `Git` specs.

## 6. Tests added

The integration test suite under `tests/` grew alongside each module. If
you change one of these areas, run the matching file first; full-suite
runs are slower because they each build a fixture tree.

- `tests/specs_*.rs` — `DepSpec::parse` classification, including the
  edge cases around `git+ssh://` vs `git@host:path` shapes.
- `tests/overrides_*.rs` — `OverrideTable::from_manifest` merge
  precedence, `lookup` semantics, behaviour on absent-vs-empty fields.
- `tests/manifest_overrides_*.rs` — deserialisation of the `overrides`
  field, including the path-keyed entries that are accepted-and-ignored.
- `tests/manifest_resolutions_*.rs` — same for the `resolutions` field
  and its glob entries.
- `tests/cache_git_paths.rs` — that the install command's CAS path is
  skipped for `local_source.is_some()` packages and that `git+` deps end
  up on disk in the expected location.
- `tests/cli_audit_*.rs` — the `guroku audit` command end-to-end against
  a stub advisories endpoint.
- `tests/audit_*.rs` — `audit::run` request shape and `print_report`
  output formatting.
- `tests/error_v05_display.rs` — `Display` smoke test for each of the
  four new `GurokuError` variants.

## 7. Integration gaps

v0.5 ships with unit-test coverage in every new module, but a handful of
paths have no live integration test. These are knowingly-shipped gaps,
not oversights — closing them required infrastructure (a real git
remote, a real advisories endpoint, a real `file:` install fixture) that
would have slowed the milestone. They are listed here so a contributor
picking up follow-up work knows what to harden first.

- **`git::ensure_cloned`** — the unit tests cover argument assembly and
  error propagation by stubbing the `git` binary, but no test actually
  clones a repository. Real-world breakage modes (auth prompts on
  private repos, network timeouts, `git` not on `PATH`) are uncovered.
- **`RegistryClient::http_post_json` against the audit endpoint** — the
  `tests/audit_*.rs` files exercise the request body construction and
  the response rendering, but the HTTP call itself is mocked. There is
  no test that talks to a real npm-compatible advisories endpoint.
- **`file:` dep end-to-end install** — covered manually via the example
  under `examples/file-dep/`, but no test in `tests/` runs a full install
  with a `file:` dependency. The unit tests for `DepSpec::parse` and
  `Resolved::local_source` cover the data flow; only the install-side
  glue is uncovered.

If you add coverage in any of these areas, no need to gate it behind a
feature flag — just add `#[ignore]` if it requires network and let CI
opt in.

## 8. Where to extend next

Concrete pointers if you are picking up follow-up work. Each line names
the nearest module so you can start reading without grepping.

- **Workspace inter-dep linking** — touch `src/resolver.rs` (treat
  workspace members as locally-rooted, the same way `File` deps are
  today; `local_source` already exists as the carrier) and
  `src/linker.rs` (use a symlink rather than a hardlink so in-tree edits
  are visible across the workspace). The discovery in
  `src/workspaces.rs` is already enough input.
- **PubGrub resolver** — replace the BFS in `src/resolver.rs` with a
  `pubgrub` `DependencyProvider`. The `DepSpec` enum is already the
  right shape for `pubgrub`'s package abstraction; the missing piece is
  the version-listing callback, which would wrap
  `RegistryClient::registry_for` + the existing manifest-fetch path.
- **Path-keyed overrides** — extend `src/overrides.rs::lookup` so it
  walks the resolution path (a `&[&str]` of ancestor names) rather than
  taking a bare name. The resolver already has the path in scope when it
  calls `lookup`; the only public API change is the signature of
  `lookup` itself.
- **Audit `--json`** — `audit::print_report` already takes a writer, but
  the format is hard-coded. Make it polymorphic on a small `Renderer`
  trait (with `Human` and `Json` impls) and select between them in
  `commands::audit::run` based on the new `--json` flag.

For anything else, start at the module map in section 2 and follow the
imports — v0.5's surface is shallow on purpose, and most of the new code
is in modules under 200 lines.
